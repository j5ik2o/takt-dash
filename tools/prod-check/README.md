# prod-check

taktDash の本番を検証するスクリプト。不具合が修正されたかどうかは、このスクリプトの合否で判定する。

## 使い方

```sh
make prod-check BASE_URL=http://10.0.1.143:3000
make prod-check BASE_URL=http://100.106.166.1:3000 WITH_E2E=1
python3 tools/prod-check/prod_check.py --base-url http://127.0.0.1:3000
```

終了コードは、0 が合格、1 が不合格、2 が確認できず（合格でも不合格でもない検査がある）。ただし make 経由では GNU make がレシピの失敗を一律に 2 へ変えるため、1 と 2 を区別できない。終了コードで判定するジョブは、make を経由せず `python3 tools/prod-check/prod_check.py` を直接実行すること。

## 検査の内容

- 版の一致：画面の frontend と backend のコミットが一致し、状態配信の buildInfo とも一致し、稼働中のコミットが展開先の HEAD とも一致すること。buildInfo が無ければ確認できずになる。
- main の展開：展開先の HEAD が origin/main を含むこと。版が一致していても、修正が未展開なら不合格になる。origin の取得に失敗した場合は、古い参照では判定せず確認できずになる。
- データの鮮度：状態配信の readAt とプロジェクトごとの lastReadAt が読み取り間隔の 2 倍以内で、切断や遅延のプロジェクトが無いこと。最終読み取り時刻が無いプロジェクトは、まだ読めていないとして不合格になる。
- 読み取りサイクル：backend の起動後のサイクルを集計し、成功率と、起動・初期化の失敗（道具の呼び出しが 0 件の失敗サイクル）と道具ごとの時間切れを分けて数える。計測の項目が無いサイクルの行（main の backend が出す形）も数え、その場合は道具の内訳は不明として扱う。
- ページ：主要ページが 200 で、エラーの文言（「backend に接続できません」「応答なし」「コミットが不一致です」）が無いこと。
- 書き込みの境界：空の本文の POST が、同じオリジンで 400（入力検証）、別のオリジンで 403、text/plain で 415 になること。空の本文は route の入力検証で止まり backend へ届かないため、本番の状態は変わらない。
- 設定の縮退（警告のみ）：プロジェクト数と読み取り間隔が期待値（既定は 20 件と 30 秒）と違うことを警告として出す。合否には影響しない。
- e2e（WITH_E2E=1 のとき）：e2e-prod の smoke を接続先へ向けて実行する。軽い検査で不合格がある場合は、Chrome を起動しない。

失敗した検査があれば、backend と Web のログから抜粋を報告へ含める。ログの全文は /tmp/prod-check-<日時>/ へ書く。

## 呼び出し方

再展開ジョブの完了条件と、定期実行の両方から呼ぶ。再展開の最中など、確認できない状態は終了コード 2 で表す。不合格のときは報告だけを行い、巻き戻しは人の判断とする。
