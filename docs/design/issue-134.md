## 何をどう変えるか

### 採用する承認の条件（1 つ）

迷う入力は承認しない（赤にする）側に倒す。打ち消し・逆接・引用の読みで規則が増えても、判定に迷う形は承認と数えない。守りの仕組みなので、取りこぼし（赤のまま）は人が1行返信すれば直るが、誤った緑は誰も気づかない（元帥、2026-11-28）。

後のコメント `a` が、次を**すべて**満たすときだけ、項目 `c` を承認したとみなす。

1. `a` は対象より後である（`a.createdAt > c.updatedAt`。対象の最終編集より後）。
2. `a` は承認できる人による。作成者（`pr_author`）、または Codex の確認コメント、または作成者が Bot のときの OWNER / MEMBER / COLLABORATOR。**作成者以外の第三者のコメントは承認に数えない**（いまも数えていない）。
3. `a` は自動報告ではない。自動報告は判定の前に候補から外す（「判定の順序」）。自動報告かどうかは文面の語句ではなく、**著者が作成者で本文がフェンスだけ**（散文が無い）であること、または**著者が作成者で、フェンスの外に `<!-- takt:auto-report -->` を持つ**ことで決める。散文がある投稿（`対応しました\n```\n…引用…\n``` ` や、マーカー付きの報告を引用した確認）は自動報告にしない。確認の語や 20 文字以上の引用を含んでいても、自動報告なら承認にしない。**いまは作成者名義の自動投稿が承認として通るので、ここを塞ぐ。**
4. `a` は**確認の語**を含む。`確認しました` / `確認いたしました` / `確認済み` / `承知しました` / `了解しました` / `対応しました` / `対応いたしました` / `対応済み` / `対処しました` / `修正しました` / `直しました` / `acknowledged` / `addressed` / `fixed`（英語は単語境界、大小文字を問わない）。`対処しました`、`直しました`、`対応いたしました`、`確認いたしました` は v1 が受けていた正当な語なので一覧に残す。語として数えるのは**作成者が自分の文で書いた、打ち消されていない語**だけである（2 回目の直し）。コードフェンス（バッククォート 3 つ、またはチルダ 3 つで囲んだ部分）・行頭 `>` の引用・「」『』“” の中・インラインのコード・項目の本文を写した部分・HTML コメント（`<!-- … -->`）・URL の中の語は数えない（HTML コメントと URL は 4 回目の直し）。直前の否定（`未`、`まだ`、`not` など）、英語の助動詞を挟む否定（`has not been fixed`、`hasn't been fixed`）と条件・未来（`once this is fixed`、`will be fixed`）、日本語の後ろに付く否定（`確認済みではありません`、`対応済みでない`）、疑問（`確認しましたか？`、`確認済みですか`、`Is it fixed?`）の語も数えない。打ち消し・条件・疑問の語も、HTML コメントと URL の中にあるものは読まない（`https://github.com/acme/pending/pull/7#issuecomment-10 を確認しました` を打ち消しにしない）。規則の全体は「確認の語の効く範囲と打ち消し」と「HTML コメントと URL の中の語」に書く。フェンスの境界は「フェンスの境界」の規則で決める。
5. `a` は**対象を一意に指す値**を、完全な形で含む。次のいずれか。**4 の語と 5 の値は、`a` の同じ単位（段落・リストの項目・節）になければならず、`a` のどこかが対象を「まだ」と打ち消していてはならない**（2 回目の直し。「確認の語の効く範囲と打ち消し」）。
   - **対象のコメントの id**。対象の URL（`https://github.com/o/r/pull/N#issuecomment-123` や `…#pullrequestreview-4`）の全体、またはそのアンカー（`#issuecomment-123` / `#pullrequestreview-4`）。アンカーの直後に数字が続く場合は一致としない（`#issuecomment-10` は `#issuecomment-101` に当たらない）。URL の全体はアンカーを含むので、照合はアンカーで足りる。**id は本文の長さを問わず、そのまま承認に使える。**
   - **対象だけが持つ本文の断片**。URL を両方の本文から外して正規化したあとの、連続する **20 文字以上**の部分で、対象の本文にあり、**この PR のほかの項目のどれにも無い**もの。引用符の有無は問わず、**コードフェンスで囲んだ引用も対象にする**（人が対象を引用するときにフェンスを使うのは自然なので、フェンス内の本文も照合する）。実装は、`a` の 20 文字の窓をすべて取り、対象の本文に含まれ、ほかの項目の本文に含まれない窓が 1 つでもあれば一致とする。**20 文字の下限は、この断片のときにだけ掛かる。**

正規化は、HTML コメント（`<!--` から `-->` まで。途中に `>` があってもそこで切らない）と HTML タグを空白にし、行頭の `>` を外し、Markdown の強調・見出し・表の記号（`*`、`_`、バッククォート、`#`、`>`、`|`）を空白にし、空白を 1 つに畳んで前後を除き、ASCII を小文字にする。コードフェンス（バッククォート 3 つ、またはチルダ 3 つ）は残す（コードの引用は正当な参照なので消さない）。確認の語の判定だけは、先に両方のフェンスを空白にする。つまり、**引用の照合はフェンス内の本文を対象にし、フェンスを外すのは確認の語の判定だけ**である。確認の側では、単位に分ける前に HTML コメントを本文から除くので、HTML コメントの中の id も断片も参照にならない（4 回目の直し）。**id はこの正規化を通さない。** `#` を空白に落とす正規化を通すと、`#issuecomment-123` が本文側で消えて一致しなくなるため、正規化前の本文（大小文字だけ揃えたもの）に対して照合する。

**断片の照合の前に、URL を両方の本文から外す**（[j5ik2o/ci#44](https://github.com/j5ik2o/ci/issues/44)）。外すのは `https?://` から空白・`)`・`>`・`]` の手前までと、scheme の無い `ホスト名/パス`（`github.com/j5ik2o/ci` の形）である。scheme の無い形は、最後のラベルがファイルの拡張子の一覧（`js`・`mjs`・`cjs`・`jsx`・`ts`・`tsx`・`json`・`yaml`・`yml`・`toml`・`lock`・`txt`・`kt`・`kts`・`scala`・`sbt`・`qnt`・`html`・`htm`・`css`・`go`）にあるときは外さない（3 回目の直し）。前の正規表現は `node.js/lib/internal/loader.js` のような拡張子つきの名前もホスト名として外し、その文を引用した正当な確認を赤にしていた（2026-11-28 に確かめた）。`scripts/x.sh`・`src/main.rs` は、前から外れない（直前が `/` の名前は頭にならない）。一覧に無い名前はホスト名として外す。断片の照合では、外し過ぎは引用が使えなくなるだけで赤の側、外し損ないは URL の頭が当たる偽の緑の側なので、一覧は狭くする。4 回目の直しで、確認の極性を見る masked でも URL を空白にした。そこでは逆に、外し過ぎが見えている打ち消しや疑問を消して緑の側に倒れるので、同じ形の正規表現で、範囲だけを狭く取る（「HTML コメントと URL の中の語」）。`rs`・`sh`・`md`・`py` は実在の国別ドメイン（`docs.rs`・`lib.rs`・`bun.sh`）、`java` は実在の gTLD なので一覧に入れない（`docs.rs/serde/…` は外れることを確かめた）。URL は id の照合にだけ使う。外さないと、`https://github.com/j`（ちょうど 20 文字）のような**どの URL にも共通の頭**が窓として一致し、作成者が別件の URL を貼って「確認しました」と書くだけで、リポジトリへのリンクを含む項目（Codex の要約など）がすべて承認になる。ci#43 の 442d679 で実際に起きた（項目に `…/g2g/blob/abc123/src/retry.rs#L10`、確認に `別件の https://github.com/j5ik2o/ci/pull/43 を確認しました` で `got 0 / success`）。項目の URL の中のパス（`src/retry.rs#L10`）も照合に使えなくなるので、その項目を指すには項目の URL を貼るか、URL の外の文を引用する。

**ほかの項目にもある断片は使わない**（[#443](https://github.com/j5ik2o/takt-dash/issues/443)）。Codex の要約の見出しやボットのレート制限の通知のような定型文は、同じ PR の複数の項目に現れる。その引用はどの項目を指すかが定まらないので、1 つの確認で別の項目まで承認しないよう、どの項目の承認にも使わない。同じ文の項目が複数あるときは、それぞれの URL（アンカー）を貼る。「ほかの項目」は、自動報告を外した候補のうち項目（`is_item`）であるもので、承認済みかどうかは問わない（判定が承認の順に依存しないため。I5）。既定で外した Codex の利用上限の通知も「ほかの項目」に数える（3 回目の直し。「Codex の利用上限の通知を既定で外す」）。

補足すると、この条件は「明示の印」と「対象を一意に指す値」の連言で、2 回目の直しでその連言を確認の全体ではなく単位ごとに取る形にした。参照だけでは #131 の失敗報告が通り、確認の語だけでは対象を指せない（後述）。20 文字は、実測で観測した最短の正当な引用（`Action not completed` の 20 文字）に合わせた。これより短いと、一般的な語が偶然一致しやすくなる。id にはこの下限がないので、対象本文が 20 文字未満でも、URL かアンカーを貼れば承認できる。

### 一意に指す値として何を使うか

項目（トップレベルコメントとレビュー要約）を一意に指す値の候補を比べた。

| 候補 | 一意か | 作成者が書けるか | 採否 |
| --- | --- | --- | --- |
| コメントの URL の全体 | 一意（アンカーに id を含む） | 関門の要約がそのまま出すので、貼るだけ | **採る**（照合はアンカーで足りる） |
| アンカー（`#issuecomment-N` / `#pullrequestreview-N`） | 一意（N は GitHub の databaseId で、種別ごとに GitHub 全体で一意。PR を書かなくても別の PR と取り違えない） | URL の末尾を写すだけ | **採る** |
| 項目だけが持つ 20 文字以上の断片（URL を除く） | この PR の項目の中で一意 | 引用するだけ。いまの確認の大半がこの形（下の実測） | **採る**（ほかの項目にある断片と URL は使わない） |
| 20 文字の窓（URL の頭や定型文を含む。ci#43） | 一意でない | — | 採らない（ci#44 と #443 の穴） |
| スレッドの id | — | — | 対象外。レビューのスレッドは解決（resolve）で外れ、承認の判定の対象ではない |
| GraphQL の node id（`IC_kwDO…`） | 一意 | 画面に出ず、人が書けない | 採らない |
| PR 番号と項目の順番（「#431 の項目 2」） | 一意でない | 書けるが、項目の順番はコメントが増えると変わる | 採らない |
| 接頭辞の無い databaseId（`comment6767269753`、`レビュー 5841855907`） | 数字だけでは run id や SHA の数字部分と区別できない | 実際に書かれている（event-store-adapter-kotlin#906） | 採らない。アンカーの形にしてもらう |

id（URL・アンカー）を第一の手段にする。引用を残すのは、いまの確認の大半が引用だけで書かれているためである（下の実測）。引用をやめて id だけにすると、event-store-adapter-java#871 の CodeRabbit の通知への確認（01:42 の引用）が赤になり（#131 の実際の確認 02:49:20 も、通知を項目に残す設定では赤になる。v2 では通知が既定で外れる）、「採らなかった案」の「URL だけ」と同じ移行の負担が出る。断片を「その項目だけが持つもの」に限れば、断片も PR の中で項目を一意に指す値になり、完全一致（部分文字列としての一致）で照合できる。

### フェンスの境界

確認の語（条件 4）、フェンスの外のマーカー、フェンスだけの本文（条件 3）の 3 つの判定は、**同じ 1 つのフェンスの境界**で決める（jq の `fence_split`）。境界を判定ごとに別の正規表現で取ると、同じ本文で「フェンスの中」の範囲が食い違う。

- 行頭（空白 3 つまで）のバッククォートかチルダが 3 つ以上並ぶ行でフェンスが開く。情報文字列（```` ```text ```` の `text`）があってもよい。
- 開きと同じ文字が、開きと同じ数以上だけ並ぶ行で閉じる。4 つのバッククォートで開いたフェンスは、中の 3 つのバッククォートの行では閉じない（マーカー付きの報告を 4 つのバッククォートで引用した確認で、中のマーカーをフェンスの外とみなさない）。
- 閉じないフェンスは本文の終わりまで続く（CommonMark と同じ）。閉じないフェンスの中の確認の語は数えない。
- Codex の文頭一致（`trusted_acknowledgement`）だけは、フェンスを外す前の本文の先頭で見る（v1 と同じ）。先頭のフェンスを外してから見ると、ログのあとの `Acknowledged` が文頭扱いになり、未修正の指摘が続く要約が項目から消える。

### 確認の語の効く範囲と打ち消し（2 回目の直し）

b808a29 の規則は、確認の語を「本文のどこかにあるか」で見て、対象への参照も本文の全体で探していた。[j5ik2o/ci#43](https://github.com/j5ik2o/ci/pull/43) のレビューで、次の 4 つの穴が見つかった（どれも ci#43 の 86a443c の `scripts/review-thread-resolution.sh` と同じ形で、設計の jq でも残っていた）。

| 穴 | 反例（b808a29 では承認になる） | 規則 |
| --- | --- | --- |
| 1. まとめ返信の語が別の項目にも効く | `- #issuecomment-10 は未対応です\n- #issuecomment-11 は対応しました` で 10 も承認。`#issuecomment-1 は確認しました。#issuecomment-2 は未対応です。` で 2 も承認 | 語と参照を同じ単位で結ぶ。打ち消しの単位が触れた項目は承認しない |
| 2. 行頭 `>` の引用の中の `fixed` | `> Once this is fixed, please rerun …` を引用して `Which tests should I run?` とだけ書くと承認（引用が参照も満たす） | 引用・項目の写しの中の語は数えない。引用は参照にだけ使う |
| 3. `not been fixed` などの英語の否定 | `This has not been fixed. #issuecomment-10` で承認（直前だけを見るので `been` を挟むと漏れる） | 同じ節の前に否定・条件・未来の語があれば、英語の語を数えない |
| 4. `確認済みではありません` などの日本語の否定 | `確認済みではありません #issuecomment-108` で承認（後ろを見ない） | 語の直後に付く否定と疑問を見る |

#### 単位に分ける

確認の本文を、行の種別で単位に分ける。フェンスの境界は「フェンスの境界」の規則のまま（`fence_split` と同じ開きと閉じ）。

- 行の種別：フェンスの中、引用（フェンスの外で、行頭の空白 3 つまでのあとが `>`）、空行、見出し（`#` が 1〜6 個と空白）、リストの項目の頭（`-`・`*`・`+`・`1.`・`1)` と空白）、それ以外の文。
- **散文の単位**は、段落（空行・見出し・引用・フェンス・リストの項目の頭で切れる、文の行の続き）、リストの項目（頭の行と、それに続く文の行。空行のあとでも、空白 2 つ以上で字下げした文の行は項目の続き。GitHub の表示と同じ）、見出しの行の 3 つ。見出しで節が切れるので、別の見出しの節の語は効かない。
- **かたまり**は、続く引用の行の並びと、1 つのフェンス。かたまりは次の順で、**同じ見出しの節の中の** 1 つの散文の単位に付く（見出しを越えて付かない。`確認しました。\n\n## B\n> #10` の引用は、どの単位にも付かない）。(1) 空行を挟まずにすぐ上にある段落かリストの項目（すぐ上がかたまりなら、その付く先）、(2) なければ下にある最初の段落かリストの項目（GitHub の「Quote reply」は引用を先に置く）、(3) なければ上にある最後の段落かリストの項目、(4) どれも無ければどこにも付かない。付いたかたまりの本文は、付く先の単位の参照（id と断片）にだけ使い、確認の語は数えない。
- CommonMark の怠惰な続き（`>` の行のすぐ下の、`>` の無い行も引用に含める規則）は採らない。`> 引用\n確認しました` の 2 行目は作成者の文として数える。画面では引用の中に見えるが、作成者が書いた文なので、赤にしない側に倒す。

#### 節に分けて極性を決める

散文の単位を、句点・感嘆符・疑問符（全角と半角）・読点（`、`・`，`・`,`）・セミコロン・改行と、空白か終わりが続くピリオドで節に分ける。読点の無い逆接（`ましたが`・`ですが`・`でしたが`・`ませんが`・`けれども`・`けど`・`ものの`、英語の `but`・`however`・`although`・`whereas` の前）でも切る（`#10 は確認しましたが #11 は未対応です`、`#10 is fixed but #11 is not fixed`）。「」『』“”（）() の中と、インラインのコードの中では切らない（`「You have reached your Codex usage limits for code reviews.」` のピリオドで切らない）。インラインのコードは CommonMark と同じく、同じ長さのバッククォートの列で開いて閉じる（``` ``fixed`` ``` も 2 つの列で囲んだコード）。閉じる列の無いバッククォートは、ただの文字として扱う。

節ごとに、確認の語を探す文字列（masked）を作る。「」『』“” の中身とインラインのコードを空白にし、さらに**項目の本文を写した部分**と **URL**（4 回目の直し）を空白にする。URL の中では節も切らない（`?`・`,`・`;` を含む URL）。写しは、単位の本文（小文字）の 20 文字の窓のうち、項目のどれかの `quote_text` に含まれるものとする（単位の全体で印を付けてから節に分ける。読点で切ってから見ると、`Once this is fixed,` のような 20 文字未満の断片を写しと認められない）。`Action not completed / Review rate limited\n確認しました。` のように項目の文を括弧なしで写しても、写しの中の `not` を作成者の打ち消しと読まず、写しの中の `fixed` を作成者の確認と読まない。

節の極性は 3 つ。

- **打ち消し**：masked に、打ち消された確認の語があるか、「まだ」の表明がある。打ち消されない確認の語と同じ節にあっても打ち消しにする（`#10 is fixed and #11 is not fixed` は、どの参照がどちらかを決められないので、節の全体を打ち消しにして赤の側に倒す）。
- **肯定**：打ち消しでなく、masked に打ち消されない確認の語がある。「まだ」の表明は閉じた一覧で、`未対応`・`未確認`・`未修正`・`未対処`・`未解決`・`未反映`・`未着手`・`未完了`・`まだ`・`ていません`／`ていない`／`てません`／`でいない`・`できません`／`できない`・`ではありません`／`じゃない`、英語の `not`・`never`・`cannot`・`pending`・`todo`・`tbd`・`n't`・`no longer`。`問題ありません`・`ない` 単独・`ません` 単独は入れない（`影響がないことを確認しました` を打ち消しにしない）。直後が `こと`・`の`・`と`・`旨` の一致も数えない（`エラーが出ていないことを確認しました` の `ていない` は確認した内容で、まだの表明ではない）。
- **どちらでもない**：それ以外。

確認の語の打ち消しは、語ごとに次のどれかで決める。

1. **直前の否定**（いまの規則のまま）：語の前 12 文字が `未`・`まだ`・`未だに`・`not`・`not yet`・`un-` で終わる（`未確認しました`、`not fixed`）。3 と 4 も含め、語と否定の間の強調の記号（`*`・`_`・`~`）は飛ばして見る（`**確認済み**ではありません`）。
2. **英語の語（`acknowledged`・`addressed`・`fixed`）だけ**：同じ節の、語より前に `not`・`never`・`cannot`・`no longer`・`n't` があるか（`has not been fixed`、`hasn't been fixed`、`isn't fixed`、`was not actually addressed`）、条件・未来の `if`・`once`・`until`・`unless`・`whether`・`will`・`'ll`・`going to` がある（`once this is fixed`、`will be fixed in a follow-up`）。日本語の語には当てない（`Action not completed を確認しました` の `確認しました` を打ち消さない）。節は読点とピリオドで切れるので、`Not a bug, but fixed` や `No regressions; fixed` は打ち消さない。
3. **日本語の後ろに付く否定**：語の直後が `ではありません`・`ではない`・`でない`・`じゃない`・`ではなく`・`ではなかった`・`とは言えません` など（`確認済みではありません`、`対応済みでない`）。`確認しました` などの過去形には後ろから付く否定が無いので、実際に効くのは `済み` の語である。
4. **疑問**：節が `?`・`？` で終わるか、語の直後が `か`（`です`・`でした`・`でしょう` を挟んでもよい。`から` は除く）である（`確認しましたか？`、`確認済みですか`、`Is #10 fixed?`）。b808a29 の規則は語の直後 3 文字だけを見ていたので、`確認済みですか` を承認していた。

`should be fixed now` のような推量は打ち消しにしない（作成者が直したと伝える普通の言い方なので）。

単位の極性は、節の極性を集めて決める。肯定の節だけ（とどちらでもない節）なら**肯定**、打ち消しの節だけなら**打ち消し**、両方なら**混在**、どちらも無ければ**どちらでもない**。

#### どの項目を承認するか

確認 `a` は、次のどれかで項目を指したとき、その項目を承認する（条件 1〜3 も満たすとき）。参照（id か、その項目だけが持つ 20 文字以上の断片）は「採用する承認の条件」5 のまま。

- **肯定の単位**：単位の本文と、付いたかたまりの本文のどこかが項目を指す（`Fixed. See #issuecomment-10.` のように、語と参照が別の文でもよい）。
- **混在の単位**：肯定の節の本文が項目を指す（付いたかたまりは使わない）。`#10 は確認しましたが、#11 は未対応です。` は 10 だけを承認する。
- **前置きに続くリストの項目**：どちらでもないリストの項目は、項目の並び（間の空行とかたまりは許す）のすぐ上の段落（前置き）が肯定なら、項目の本文と付いたかたまりで指した項目を承認する（`次の 2 件を確認しました。\n- #10\n- #11`）。項目に打ち消しがあれば前置きは効かない（`- #11 はまだです`）。リストのあとの締めの文（`以上を確認しました。`）は効かない。

そのうえで、**打ち消しの節が触れた項目は承認しない**（拒否）。触れるとは、打ち消しの節の本文が項目の id を含むか、URL を外した本文の 20 文字の窓が項目の本文にあること（その項目だけが持つ断片でなくてよい）。打ち消しの節を含む単位（打ち消しか混在）に付いたかたまりが触れた項目も拒否する（`この件はまだです。\n> <項目の引用>` のあとに、その項目の URL を確認しても承認しない）。`#10 と #11 を確認しました。ただし #11 はまだ直していません。` は 10 だけを承認する。定型文に打ち消しで触れると、その定型文を持つ項目はどれもその確認では承認されない（どの項目のことか定まらないので、赤の側に倒す）。

#### 誤って赤にする側

この規則が正当な確認を赤にする形と、実データでの影響は次のとおり。

- 確認の語の無い単位で項目を指す（`対象: <URL>\n\n指摘はありません。`、`<URL>: I noted it.`）。実データでは modern-ddd-book#695 と event-store-adapter-java#871 の 2 件（「一意に指す値として何を使うか」の測り直し）。その単位に `確認しました` を足せば緑になる。2 件とも指していたのは Codex の利用上限の通知で、3 回目の直しのあとは既定で外れるので赤にならない。
- リストのあとの締めの文だけに確認の語がある（`- #10\n- #11\n\n以上を確認しました。`）。30 件の標本には無かった。
- 1 つの節で、英語の否定のあとに別の英語の確認を続ける（`This doesn't affect X and is fixed`）。1 つの節で肯定と打ち消しを `and` でつなぐ（`#10 is fixed and #11 is not fixed` は 10 も承認しない）。30 件の標本には無かった。
- 1 つの確認で、承認した項目の文を打ち消しの節でも写す（矛盾する返信）。拒否が勝つ。
- 境界が決まらない HTML コメントを持つ確認（閉じない `<!--`、範囲にバッククォートか `~~~` を含むもの）は、ほかの部分の確認も含めて何も承認しない（4 回目の直し。「HTML コメントと URL の中の語」）。段落の途中の閉じない `<!--`（`確認しました #10 <!-- メモ`）は GitHub では文字として見えるが、赤になる。2026-11-28 に取り直した 45 件の確認には無かった。

逆に、この規則でも見逃す形（偽の緑の側）は「未確認のこと」に書く。

### HTML コメントと URL の中の語（4 回目の直し）

[j5ik2o/ci#43](https://github.com/j5ik2o/ci/pull/43)（先端 77ccaac）で観点 30〜33 のテストを足したとき、06770ed の jq で再現する穴が 2 つ見つかった（CodeRabbit の[スレッド 1](https://github.com/j5ik2o/ci/pull/43#discussion_r4726604859)・[スレッド 2](https://github.com/j5ik2o/ci/pull/43#discussion_r4726604865)）。この直しを書くときに、同じ根の 3 つ目（穴 7）も見つけた。どれも、極性を見る masked に HTML コメントと URL が残っていたことによる。

| 穴 | 反例（06770ed） | 規則 |
| --- | --- | --- |
| 5. HTML コメントの中の確認の語（偽の緑） | `<!-- fixed --> #issuecomment-10` と `<!-- 確認しました --> #issuecomment-10` が 10 を承認する。画面には確認の語が無い | 確認を読む前に HTML コメントを除く |

**HTML コメント**（穴 5）。確認（`acked_keys`）は、単位に分ける前に本文から HTML コメント（`<!--` から最初の `-->` まで）を空白 1 つに置き換える。中の確認の語・打ち消し・まだの表明・id・断片のどれも読まない。画面に出ない語で承認しないためで、引用・インラインのコードと同じく作成者が画面で示した文ではないとみなす。ただし引用と違い、中の id と断片も参照に使わない（`<!-- #issuecomment-10 --> を確認しました` は承認しない）。

- **ボットの印で判定を変えない**：印（`<!-- codex-review-state:v1 {"code_review":{…,"status":"failed"}} -->`、`<!-- coderabbit-ai-generated:v1 -->`、`<!-- devin-review-badge-begin -->` など。#131・#695・#871・#926 の実物）の中の語は、確認にも打ち消しにもならない。`<!-- codex-review-state:v1 {"status":"pending"} --> #issuecomment-10 を確認しました` は承認する（06770ed は印の中の `pending` を読んで赤）。`#issuecomment-10 を確認しました。<!-- #issuecomment-10 はまだ -->` も承認する。画面に出る文だけで決める。
- **境界が決まらない形は何も承認しない**（迷う形は赤に倒す）。2026-11-28 に GitHub の Markdown API（`POST /markdown`、GFM）で確かめた表示は次のとおりで、境界を正しく決めるには CommonMark のブロックとインラインの規則を写す必要がある。
  - 行頭の閉じない `<!--` は、本文の終わりまでを隠す（`確認しました #1\n<!-- 未閉じ\nfoo #2` は `確認しました #1` だけが見える）。段落の途中の閉じない `<!--` は文字として見える（`確認しました #1 <!-- 未閉じ foo #2` は全体が見える）。
  - インラインのコードとフェンスの中の `<!--` は文字である（`` `<!--` は未対応 `-->` 確認 `` は全体が見える）。そこから外の `-->` までを除くと、見えている `未対応` が消えて緑の側に倒れる。逆に、行頭の `<!--` から始まる範囲は、中のフェンスごと隠れる。

  そこで、閉じない `<!--` を持つ確認と、範囲（`<!--` から `-->` まで）にバッククォートか `~~~` を含む確認は、**ほかの部分を含めて何も承認しない**（jq の `html_comment_ambiguous`）。どちらの読みを選んでも、片方では見えている打ち消しを消すためである。作成者が HTML コメントを使わずに書き直せば緑になる。
- **ほかの判定は変えない**：HTML コメントを除くのは確認を読む所（`acked_keys`）だけである。自動報告の印（`has_takt_marker`。印そのものが HTML コメント）、フェンスだけの本文（`fenced_report_body`）、Codex の文頭一致（`ack_at_start`）、既定で外す通知の頭（`default_ignored_notice`）は、取得した本文をそのまま見る。項目の側の正規化（`norm_text`）は、前から閉じた HTML コメントを除いており、正規表現を共有する形にしただけで振る舞いは変えない（閉じない `<!--` も前のまま残す。項目から文を除くと「ほかの項目」の文が減り、断片が固有になりやすくなって緑の側に動くため）。

**URL**（穴 6・7）。節の masked で、URL を同じ長さの空白にする（jq の `url_flags`。断片の照合で URL を外す `strip_urls` と同じ形の正規表現 `blank_urls` で、scheme つきと scheme の無いホスト・パスの両方。範囲だけを用途で分ける。下の「URL を広く取らない」）。URL の中の確認の語・打ち消し・条件・疑問の語を読まず、URL の中では節も切らない。id の照合は前のまま元の本文で行うので、URL の中のアンカーは参照に使える。打ち消しの節の拒否（`mentions_in`）も元の本文で照合する。

- **URL を広く取らない**：masked で URL を空白にすると、URL の範囲に入った文は打ち消しとしても読まれない。06770ed の `[^\s)>\]]+` は空白まで続くので、空白なしで続く日本語も URL に入る。`次を確認しました。\n- https://…#issuecomment-10\n- https://…#issuecomment-11はまだです` で `はまだです` が消え、前置きの語が効いて 11 も承認する（偽の緑。この直しの jq の URL の文字を空白までに戻した版で確かめた）。`Is #issuecomment-10 fixed in https://github.com/o/r/pull/2?` も、終わりの `?` が URL に入って疑問と読まれず、承認する（同じ版）。そこで、masked では URL の文字を ASCII の印字できる文字（`)`・`>`・`]` を除く）に限り、終わりの `?`・`!`・`.`・`,`・`:`・`*`・`_`・`~` を URL に入れない（GFM の自動リンクと同じ）。
- **断片の照合は広いまま**：断片の照合（`strip_urls`）は、06770ed と同じく空白・`)`・`>`・`]` の手前まで外す。ここでは向きが逆で、狭く取ると、ASCII でない文字を含む URL（`https://github.com/o/r/blob/main/docs/設計/…`）や IDN のホスト（`https://日本語のドメイン.example.com/…`）の後ろが本文に残り、別件として同じ URL を貼った確認が 20 文字の窓で項目を承認する（偽の緑。観点 8(b)〜(d) の後退。masked と同じ狭い範囲にした版で確かめた）。正規表現の形は 1 つ（`blank_urls`）で、URL の文字と終わりの文字だけを、それぞれの用途で赤に倒れる側に取る。中将の決め（断片の照合の前に URL を外すのと同じ前処理にそろえる）とは、範囲が違う点でずれる。
- **見逃す形**：ASCII でない文字を含む URL（`https://ja.wikipedia.org/wiki/日本`）は、masked では ASCII の所までが URL になり、残りは作成者の文として読む（残りの確認の語も打ち消しの語も数える）。

### 判定の順序（自動報告を先に外す）

自動報告は、承認の条件を 1 つずつ当てる前の**候補選別**で外す。順序を固定しないと、確認の語と引用を含む失敗報告が自動報告の除外を通り抜け、条件 4 と 5 を満たして通ってしまう。

ここでは除外を **ack の判定より前**に置き、除外した投稿が項目にも承認にも数えられないことを順序で保証する。

1. 取得したトップレベルコメントとレビュー本文のすべてから、自動報告を除く（`$candidates`）。
2. 自動報告は、既存の `ignored_auto_report`（v1 の著者＋本文パターン。CodeRabbit の要約、Codex の要約の見出し `Codex Review` など）に、**既定で外す通知**（Codex の利用上限の通知。作者と本文の頭の両方で当てる。次の節）と **TAKT の失敗報告の種別**を足したものである。既存のパターン一覧は、いまの項目の選び方を変えないためにそのまま使う。TAKT の失敗報告として新しく足すのは次の 2 つの種別だけで、どちらも本文の語句（`対応しました`、`確認しました` など）では判定しない。
   - **フェンスだけの本文**：著者が作成者（`pr_author`）で、本文からコードフェンス（``` または ~~~）を取り除くと空白だけになる投稿（散文が無い。#131 の実測形）。散文がある投稿は、フェンスの直前に一文だけ置く形（`対応しました\n```\n…引用…\n``` `）も含めて自動報告にしない。行数とフェンスの形だけで決め、文面は見ない。
   - **マーカー**：著者が作成者で、**フェンスの外に** `<!-- takt:auto-report -->` を持つ投稿。TAKT が付ける将来の印で、フェンスの外に自由な文を書ける。TAKT は作成者名義で投稿するので、著者条件で足りる。第三者が付けたマーカーは効かない（著者が作成者のときだけ種別と認める）。マーカー付きの報告をフェンスで引用した確認では、マーカーがフェンスの中に入るので種別と認めない。
3. 残った候補から、項目（`is_item`）と承認の候補（`is_acknowledger`）を選ぶ。項目選別の中では `trusted_acknowledgement`（文頭一致）だけを見る。
4. 承認は、残った候補のうち条件 1〜5 をすべて満たすものだけを数える。確認の語は承認の判定（`acked_keys`。単位ごとの語と参照）で評価し、項目選別では見ない。

代表例：作成者が `対応しました\n```\n…対象の引用…\n``` ` を投稿すると、散文があるので自動報告にしない。フェンス内の引用が対象を指し、フェンスの外の `対応しました` が確認の語なので、**承認として通る（赤にしない）**。自動報告として赤くなるのは「本文全体がフェンス」の形だけである。`<!-- takt:auto-report -->` 付きの散文報告（`<!-- takt:auto-report -->\n対応しました\n…引用…`）は、フェンスの外のマーカーがあるので自動報告として `$candidates` から落ちる。マーカー付きの報告をフェンスで引用した確認は、マーカーがフェンスの中なので自動報告にならず、散文の確認の語とフェンス内の引用で通る。

自動報告は項目にも承認にもならない（I3）。TAKT の失敗報告が将来散文を伴う形（フェンスの外に文を足す形）になるときは、`<!-- takt:auto-report -->` を付けることを TAKT 側の移行条件にする（「適用と移行」）。

### Codex の利用上限の通知を既定で外す（3 回目の直し）

v2 は、Codex の利用上限の通知を**共有の既定で**自動報告として外す（元帥の決め、2026-11-28）。前の版（d7e6d5b）の「v2 の既定には入れず、呼び出し側の設定をそのまま使う」（リポジトリごとの 3 行）は取り消す。

- **経緯**：2026-11-13 の全プロジェクト統一仕様の 4 は「関門で Codex の利用上限の通知を除外しない」で、takt-dash も #423 で足していた呼び出し側の除外を #455（a49595b）で外した。2026-11-28 にオーナーが「除外するか、毎回コメントして対応するかは任せる」と述べ、元帥はこの点で統一仕様の 4 を置き換えて、v2 の既定で外すと決めた。
- **当て方**：作者（`report_author_login` が `chatgpt-codex-connector`。GraphQL の `chatgpt-codex-connector` も REST の `chatgpt-codex-connector[bot]` も同じ）と、本文の頭（取得した本文そのものが `You have reached your Codex usage limits` で始まる）の**両方**が一致したときだけ外す（jq の `default_ignored_notice`）。頭は、先頭の空白・改行・HTML コメント・`>` を飛ばさず、大小文字も区別して見る。既存のパターンの当て方（`contains`。本文のどこか）とは違う。実物の通知は 2 つの文言（`… for code reviews. You can see your limits …` と `… usage limits. You can see your limits …`。event-store-adapter-kotlin#926 に両方ある）で、どちらもこの頭で始まる。
- **外さないもの**：Codex のほかのコメント（本物のレビュー、要約、指摘）は、本文が頭で始まらないので、この除外では外さない。本文の途中に通知と同じ文があっても外さない。ほかの作者が通知の文で始めたコメント（通知を写した人やボット）も外さない。Codex の要約が v1 の既存の既定（`chatgpt-codex-connector` と `Codex Review`）で外れることは変えない。
- **「迷う入力は赤に倒す」との関係**：外すのは、作者と頭の両方が一致した、確かに通知である形だけである。片方だけの一致、頭の前に空白がある、大小文字が違う、のような形は迷う入力として外さない（項目として残り、赤に倒す）。Codex が通知の文言を変えれば、その通知は項目に戻って赤になる。そのときは作成者が通知の URL つきで返信すれば緑になり、既定の一覧は `v2.1` で直す。
- **呼び出し側の入力にしない**：一覧は jq に固定し、再利用ワークフローの inputs に足さない（「何に触れるか」のとおり inputs は変えない）。`ignored_auto_report_author_patterns` を上書きしても、この除外は消えない。プロジェクトごとの個別方針は認めないので、呼び出し側に個別の除外は足さない。呼び出し側に残っている同じ通知の `extra_ignored_auto_report_author_patterns` の行は、v2 に上げる PR で消す（`contains` で当たるので、本文の途中に同じ文を含む Codex の本物のレビューまで外してしまう。「移行の順」7）。
- **承認には数えない**：外した通知は自動報告なので、項目にも承認の候補にもならない（I3）。
- **「ほかの項目」には数える**：外した通知の本文は、断片がその項目だけのものかを決めるときの「ほかの項目」に数える（jq の `$excl`）。数えないと、通知を引用した別の項目（レビュアーが通知を引用して「あとでもう一度回してください」と書いたものなど）が、いつもの `「You have reached your Codex usage limits for code reviews.」を確認しました` で承認になる。作成者が指したのは通知のほうなので、赤の側に倒す。その項目は URL で承認する（テストの観点 31）。
- **v1 は動かさない**：タグ `v1`（`2ead62a`）は動かさない。v2 に上がるまで、通知は未承認の項目として残る。作成者は通知の URL（アンカー）つきで確認の語を返信して通す（`https://github.com/o/r/pull/1#issuecomment-N の Codex の利用上限の通知を確認しました。`）。v1 は内容を見ないので通知より後の作成者のコメントならどれでも通るが、v2 の規則でもそのまま通る形で書く。

### 判定の式（jq の形）

````jq
def ack_words:
  "確認しました|確認いたしました|確認済み|承知しました|了解しました|対応しました|対応いたしました|対応済み|対処しました|修正しました|直しました|\\backnowledged\\b|\\baddressed\\b|\\bfixed\\b";

# Codex の承知の語彙。v1 と同じ狭い一覧だけを使う（条件 4 の ack_words は使わない）。
# `Fixed`・`確認済み`・`修正しました`・`直しました`・`確認いたしました`・`対応いたしました` は
# 著者自身の確認（条件 4）でだけ承認に使う。
def trusted_ack_words:
  "acknowledged|addressed|確認しました|承知しました|了解しました|対応済み|対応しました|対処しました";

# コードフェンスの境界。確認の語・マーカー・フェンスだけの本文の判定が、この 1 つを共有する。
# CommonMark と同じく、行頭（空白 3 つまで）のバッククォートかチルダ 3 つ以上で開き、
# 同じ文字で、開きと同じ長さ以上の行で閉じる。閉じないフェンスは本文の終わりまで続く。
# 4 つのバッククォートで開いたフェンスは、中の 3 つのバッククォートの行では閉じない。
def fence_open($line):
  [ $line | match("^ {0,3}(`{3,}|~{3,})") ]
  | if length > 0 then .[0].captures[0].string else null end;

def fence_closes($line; $open):
  ($open[0:1]) as $c
  | $line | test("^ {0,3}" + (if $c == "`" then "`" else "~" end)
                 + "{" + ($open | length | tostring) + ",}\\s*$");

def fence_split:
  reduce ((.body // "") | split("\n"))[] as $line (
    { open: null, prose: [], fenced: 0 };
    if .open == null then
      fence_open($line) as $o
      | if $o == null then .prose += [$line] else .open = $o | .fenced += 1 end
    elif fence_closes($line; .open) then .open = null
    else . end);

# フェンスの外の散文だけ。
def strip_fences:
  fence_split | .prose | join("\n");

# 文頭一致。v1 の `^\s*(…)` と同じく、フェンスを外す前の本文の先頭で見る。
# 先頭のフェンス（ログなど）を外してから見ると、その後ろの `Acknowledged` が文頭扱いになり、
# 未修正の指摘が続く Codex の要約が項目から消えるため。語彙も v1 と同じ trusted_ack_words だけ。
def ack_at_start:
  (.body // "")
  | ascii_downcase
  | test("^\\s*(" + trusted_ack_words + ")");

# HTML コメント。`<!--` から最初の `-->` まで（途中の `>` で切らない）。項目の照合（norm_text）と
# 確認の読み（acked_keys）が、この 1 つを共有する。自動報告の印（has_takt_marker）、フェンスだけの本文、
# Codex の文頭一致、既定で外す通知の頭は、これを通さない（4 回目の直し）。
def html_comment_re: "(?s)<!--.*?-->";

def strip_html_comments:
  gsub(html_comment_re; " ");

# 境界が決まらない HTML コメントを持つ確認（4 回目の直し）。この確認は何も承認しない（迷う形は赤に倒す）。
# 1. 閉じない `<!--`。GitHub は、行頭なら本文の終わりまでを隠し、段落の途中なら文字として見せる。
# 2. 範囲にバッククォートか `~~~` を含む。インラインのコードやフェンスの中の `<!--` は文字なので、
#    外の `-->` までを除くと、見えている打ち消し（`未対応`）まで消える。
def html_comment_ambiguous:
  (.body // "") as $b
  | ($b | strip_html_comments | test("<!--"))
    or any($b | match(html_comment_re; "g") | .string; test("`|~~~"));

# フェンスは残す（フェンス内の引用も照合の対象）。確認の語は norm_text を通さず、
# 単位と節（clauses）の masked で見る。
def norm_text($body):
  $body
  | strip_html_comments
  | split("\n")
  | map(gsub("^\\s*>\\s?"; ""))
  | map(gsub("<[^>]+>"; " "))
  | map(gsub("[*_`#>|]+"; " "))
  | map(gsub("\\s+"; " ") | sub("^ "; "") | sub(" $"; ""))
  | map(select(length > 0))
  | join("\n")
  | ascii_downcase;

def raw_body:
  (.body // "") | ascii_downcase;

# URL は id の照合にだけ使う。断片の照合の前に両方の本文から外す（ci#44）。
# 外さないと `https://github.com/j` のような URL の共通の頭が 20 文字の窓として当たる。
# scheme の無い `ホスト名/パス` は、最後のラベルがファイルの拡張子（`js`・`ts`・`json` など）なら外さない
# （`node.js/lib` を残す。3 回目の直し）。一覧に無い名前はホスト名として外す（外し過ぎは赤の側）。
# `rs`・`sh`・`md`・`py` は実在の国別ドメイン（`docs.rs`・`lib.rs`・`bun.sh`）、`java` は実在の gTLD なので一覧に入れない。
def file_ext_labels:
  "js|mjs|cjs|jsx|ts|tsx|json|ya?ml|toml|lock|txt|kts?|scala|sbt|qnt|html?|css|go";

# URL を同じ長さの空白にする（位置を保つ）。scheme つきと scheme の無いホスト・パスの両方。
# $c は URL の文字、$tail は URL の終わりに置けない文字の後読み。正規表現の形は 1 つで、範囲だけを用途で分ける（4 回目の直し）。
def blank_urls($body; $c; $tail):
  ($body // "")
  | gsub("(?i)(?<u>https?://" + $c + "+" + $tail + ")"; .u | gsub("."; " "))
  | gsub("(?i)(?<pre>^|[^a-z0-9_./-])(?<u>(?:[a-z0-9-]+\\.)+(?!(?:" + file_ext_labels + ")/)[a-z]{2,}/"
         + $c + "*" + $tail + ")"; "\(.pre)" + (.u | gsub("."; " ")));

# 断片の照合（quote_text・refs_in・mentions_in。norm_text が空白を畳む）。06770ed と同じく、URL を空白・`)`・`>`・`]` の
# 手前まで広く取る。ここでは外し過ぎが赤の側（引用が使えない）、外し損ないが緑の側（URL の中のパスや、ASCII でない
# 文字の後ろが 20 文字の窓として当たる）なので、広く取る。
def strip_urls($body):
  blank_urls($body; "[^\\s)>\\]]"; "");

# 節の masked で空白にする URL の位置の印（コードポイントごとの真偽。4 回目の直し）。ここでは逆に、外し過ぎが緑の側
# （見えている打ち消しや疑問を消す）なので、狭く取る。URL の文字を ASCII の印字できる文字（\x21〜\x7e）から
# `)`（\x29）・`>`（\x3e）・`]`（\x5d）を除いたものに限り（空白なしで続く `…#issuecomment-11はまだです` を URL に入れない）、
# 終わりの `?`・`!`・`.`・`,`・`:`・`*`・`_`・`~` も URL に入れない（GFM の自動リンクと同じ。`Is #10 fixed in https://…/2?` の `?`）。
def url_char: "[\\x21-\\x28\\x2a-\\x3d\\x3f-\\x5c\\x5e-\\x7e]";
def url_tail: "(?<![?!.,:*_~])";

def url_flags($s):
  ($s | explode) as $o
  | (blank_urls($s; url_char; url_tail) | explode) as $m
  | [ range(0; $o | length) as $i | $m[$i] == 32 and $o[$i] != 32 ];

def quote_text($c):
  norm_text(strip_urls($c.body));

def windows($n):
  . as $s | [range(0; (($s | length) - $n + 1)) as $i | $s[$i:$i + $n]];

def anchor($u):
  ($u // "" | split("#") | if length > 1 then "#" + .[-1] else "" end);

# id の完全一致。直後に数字が続く一致は数えない（#issuecomment-10 は #issuecomment-101 に当たらない）。
# 位置（indices）を使わず、正規表現の先読みで決める（3 回目の直し）。jq 1.7 までの indices はバイト位置を返し、
# 日本語の後ろで「直後の 1 文字」を取り違えて偽の緑になる（「jq の版と、位置に頼らない判定」）。
def re_escape:
  gsub("(?<c>[.^$|?*+()\\[\\]{}\\\\])"; "\\\(.c)");

def id_match($raw; $needle):
  $needle != ""
  and ($raw | test(($needle | re_escape) + "(?![0-9])"));

# ---- 確認の語の効く範囲・引用・否定（2026-11-28 の 2 回目の直し。ci#43 の残る穴 4 つ） ----

# 行の種別。フェンスの境界は fence_split と同じ規則（閉じないフェンスは終わりまで）。
# fence: フェンスの中（開き・閉じの行を含む。開きの行に start: true）
# quote: フェンスの外で、行頭（空白 3 つまで）が `>` の行
# blank / heading / item（リストの項目の頭）/ text
def line_kinds:
  reduce ((.body // "") | split("\n"))[] as $line (
    { open: null, out: [] };
    if .open == null then
      fence_open($line) as $o
      | if $o != null then .open = $o | .out += [{k: "fence", t: $line, start: true}]
        elif ($line | test("^\\s*$")) then .out += [{k: "blank", t: $line}]
        elif ($line | test("^ {0,3}>")) then .out += [{k: "quote", t: $line}]
        elif ($line | test("^ {0,3}#{1,6}(\\s|$)")) then .out += [{k: "heading", t: $line}]
        elif ($line | test("^\\s*([-*+]|[0-9]+[.)])\\s+")) then .out += [{k: "item", t: $line}]
        else .out += [{k: "text", t: $line}] end
    elif fence_closes($line; .open) then .open = null | .out += [{k: "fence", t: $line}]
    else .out += [{k: "fence", t: $line}] end)
  | .out;

# 単位の列。散文の単位（para・item・heading）と、引用・フェンスのかたまり（block）。
# gap: 直前に空行があるか。sec: 見出しで区切った節の番号（見出しの行から新しい節）。
def units:
  reduce line_kinds[] as $l (
    { us: [], gap: false, sec: 0 };
    (.us | length) as $n
    | (if $n > 0 then .us[$n - 1] else null end) as $last
    | (if $l.k == "heading" then .sec += 1 else . end)
    | if $l.k == "blank" then .gap = true
      elif $l.k == "text" and $last != null and (.gap | not)
           and ($last.type == "para" or $last.type == "item") then
        .us[$n - 1].text += "\n" + $l.t
      # 空行のあとでも、字下げ（空白 2 つ以上）した文の行はリストの項目の続き（GitHub の表示と同じ）。
      elif $l.k == "text" and $last != null and $last.type == "item" and ($l.t | test("^ {2,}\\S")) then
        .us[$n - 1].text += "\n" + $l.t | .gap = false
      elif $l.k == "quote" and $last != null and (.gap | not) and $last.type == "block" and $last.q then
        .us[$n - 1].text += "\n" + $l.t
      elif $l.k == "fence" and ($l.start | not) and $last != null and $last.type == "block" and ($last.q | not) then
        .us[$n - 1].text += "\n" + $l.t | .gap = false
      else
        .us += [{
          type: (if $l.k == "text" then "para" elif $l.k == "item" then "item"
                 elif $l.k == "heading" then "heading" else "block" end),
          q: ($l.k == "quote"),
          text: $l.t,
          gap: .gap,
          sec: .sec
        }]
        | .gap = false
      end)
  | .us;

# かたまりの付く先（散文の単位の位置）。探すのは同じ見出しの節の中だけ。
# 1. 空行を挟まずすぐ上にある散文の単位（すぐ上がかたまりなら、その付く先）
# 2. なければ、下にある最初の para か item
# 3. なければ、上にある最後の para か item
# 4. どれも無ければ null（どの単位にも付かない）
def attach_targets($us):
  reduce range(0; $us | length) as $j (
    [];
    . as $acc
    | if $us[$j].type != "block" then $acc + [null]
      elif $j > 0 and ($us[$j].gap | not)
           and ($us[$j - 1].type == "para" or $us[$j - 1].type == "item") then $acc + [$j - 1]
      elif $j > 0 and ($us[$j].gap | not) and $us[$j - 1].type == "block" and $acc[$j - 1] != null
           and $acc[$j - 1] < $j then $acc + [$acc[$j - 1]]
      else
        ([range($j + 1; $us | length)
          | select(($us[.].type == "para" or $us[.].type == "item") and $us[.].sec == $us[$j].sec)] | first) as $next
        | ([range(0; $j)
          | select(($us[.].type == "para" or $us[.].type == "item") and $us[.].sec == $us[$j].sec)] | last) as $prev
        | $acc + [($next // $prev)]
      end);

# リストの項目の前置き：項目の並び（間の空行とかたまりは許す）のすぐ上の para。
def lead_of($us; $j):
  [ range($j - 1; -1; -1) as $k | $us[$k] | {k: $k, type} ]
  | (map(select(.type != "item" and .type != "block")) | first) as $p
  | if $p != null and $p.type == "para" then $p.k else null end;

# 節に分ける。句点・感嘆符・疑問符・読点・セミコロン・改行と、空白か終わりが続くピリオドで切る。
# 「」『』“”（）() の中と、インラインのコードの中と、URL の中（$url が印を付けた文字）では切らない。
# raw: 照合に使う元の文字列。masked: 確認の語・打ち消し・まだの表明を探す文字列（「」『』“” の中身、インラインのコード、
# $cover が印を付けた項目の写し、$url が印を付けた URL を空白にする。URL は 4 回目の直し）。
# インラインのコードは CommonMark と同じく、同じ長さのバッククォートの列で開いて閉じる
# （``fixed`` も 2 つの列で囲んだコード）。閉じる列が無い列は、ただの文字として扱う。
def backtick_runs($cs):
  ($cs | length) as $len
  | [ range(0; $len) as $i
      | select($cs[$i] == 96 and ($i == 0 or $cs[$i - 1] != 96))
      | { start: $i,
          len: (([ range($i; $len) as $k | select($cs[$k] != 96) | $k ] | first // $len) - $i) } ];

def clauses($cover; $url):
  explode as $cs
  | ($cs | length) as $len
  | backtick_runs($cs) as $runs
  | ($runs | map({key: (.start | tostring), value: .len}) | from_entries) as $runat
  | reduce range(0; $len) as $i (
      { out: [], raw: [], masked: [], depth: 0, qdepth: 0, code: null };
      ($cs[$i]) as $c
      | ([$c] | implode) as $ch
      | (if $i + 1 < $len then ([$cs[$i + 1]] | implode) else "" end) as $nx
      | ($runat[$i | tostring]) as $run
      | if $run != null and .code == null
           and any($runs[]; .start > $i and .len == $run) then
          .code = $run | .raw += [$c] | .masked += [32]
        elif $run != null and .code == $run then .code = null | .raw += [$c] | .masked += [32]
        elif .code != null then .raw += [$c] | .masked += [32]
        elif $ch == "`" then .raw += [$c] | .masked += [32]
        # URL の中の文字は空白にし、括弧の深さも変えず、節も切らない（`?`・`,`・`;` を含む URL）。
        elif ($url[$i] // false) then .raw += [$c] | .masked += [32]
        else
          (if ($ch | test("^[「『“]$")) then .qdepth += 1 | .depth += 1
           elif ($ch | test("^[」』”]$")) then .qdepth = ([0, .qdepth - 1] | max) | .depth = ([0, .depth - 1] | max)
           elif ($ch | test("^[（(]$")) then .depth += 1
           elif ($ch | test("^[）)]$")) then .depth = ([0, .depth - 1] | max)
           else . end)
          | .raw += [$c]
          | .masked += [(if ($cover[$i] // false) or (.qdepth > 0 and ($ch | test("^[「『“」』”]$") | not)) then 32 else $c end)]
          | if .depth == 0
               and (($ch | test("^[。！？!?；;、，,\n]$"))
                    or ($ch == "." and ($nx == "" or ($nx | test("^\\s$"))))) then
              .out += [{raw: (.raw | implode), masked: (.masked | implode)}] | .raw = [] | .masked = []
            else . end
        end)
  | .out + (if (.raw | length) > 0 then [{raw: (.raw | implode), masked: (.masked | implode)}] else [] end)
  | map(select(.raw | test("\\S")));

def en_ack_words: "\\backnowledged\\b|\\baddressed\\b|\\bfixed\\b";

# 確認の語の打ち消し。$s は節の masked を小文字にしたもの、$m は語の一致。
def negated2($s; $m):
  ($s[0:$m.offset]) as $before
  | ($s[($m.offset + ($m.string | length)):]) as $after
  # 直前の否定（いまの規則のまま）
  | ($s[([0, ($m.offset - 12)] | max):$m.offset]
     | test("(未|まだ|未だに?|\\bnot\\b|\\bnot\\s+yet\\b|\\bun-?)[\\s*_~]*$"))
  # 英語：同じ節の前に否定・条件・未来の語（has not been fixed / hasn't been fixed / once this is fixed）
  or (($m.string | test(en_ack_words))
      and ($before | test("\\b(not|never|cannot|no longer|unless|until|if|once|whether|will|going to)\\b|n['’]t\\b|['’]ll\\b")))
  # 日本語：後ろに付く否定（確認済みではありません / 対応済みでない / とは言えません）
  or ($after | test("^[\\s*_~]*((では|じゃ|で)は?\\s*(ありません|ない|なく|なかった)|とは(言え|いえ)(ません|ない))"))
  # 疑問（確認しましたか / 確認済みですか / Is it fixed?）
  or ($after | test("^[\\s*_~]*(です|でした|でしょう)?\\s*か(?!ら)"))
  or ($s | test("[?？]\\s*$"));

# まだの表明（確認の語が無くても、その節は「打ち消し」になる）。
def pending_cue:
  "未(対応|確認|修正|対処|解決|反映|着手|完了)|まだ|(て|で)い?(ません|ない|なかった)|でき(ません|ない)|(では|じゃ)(ありません|ない)|\\b(not|never|cannot|pending|todo|tbd)\\b|n['’]t\\b|\\bno longer\\b";

# 項目の本文を写した部分の印（$s は単位の本文を小文字にしたもの、$texts は項目の quote_text）。
# 20 文字の窓が項目のどれかの本文にあれば、その 20 文字を作成者の文ではないとみなす。
# 項目の文の `not`・`まだ`・`fixed` を、作成者の打ち消しや確認と読まないため。単位の全体で見てから節に分ける
# （節に分けてから見ると、読点で切れた 20 文字未満の断片を写しと認められない）。
def cover_flags($s; $texts):
  ($s | explode | length) as $len
  | (reduce range(0; ([0, $len - 19] | max)) as $i (
      [range(0; $len) | false];
      if any($texts[]; contains($s[$i:$i + 20])) then reduce range($i; $i + 20) as $k (.; .[$k] = true) else . end));

# まだの表明の一致。直後が `こと`・`の`・`と`・`旨` の一致は数えない（`エラーが出ていないことを確認しました` の
# `ていない` は、確認した内容であって、まだの表明ではない）。
def pending_hits($s):
  [ $s | match(pending_cue; "g")
    | select(($s[(.offset + (.string | length)):] | test("^\\s*(こと|の|と|旨)")) | not) ];

# 節の極性：pos（打ち消されない確認の語があり、打ち消しもまだの表明も無い）/
# neg（打ち消された語かまだの表明がある。打ち消されない語と同じ節にあっても neg）/ none。
# 同じ節に肯定と打ち消しが並ぶとき（`#10 is fixed and #11 is not fixed`）は、どの参照がどちらかを
# 決められないので、節の全体を打ち消しにして赤の側に倒す。
# 語・打ち消し・まだの表明は masked（引用・インラインのコード・項目の写しを空白にしたもの）で見る。
def polarity:
  (.masked | ascii_downcase) as $s
  | [ $s | match("(" + ack_words + ")"; "g") ] as $hits
  | ([ $hits[] | select(negated2($s; .) | not) ] | length) as $pos
  | (($hits | length) - $pos) as $negw
  | (pending_hits($s) | length) as $cue
  | if $negw > 0 or $cue > 0 then "neg"
    elif $pos > 0 then "pos"
    else "none" end;

# 節を切る前に、逆接の接続（`ましたが`・`ですが`・`けど`・`ものの`、英語の `but`・`however`・`although`・
# `whereas`）の位置に改行を入れる。読点の無い `#10 は確認しましたが #11 は未対応です` や
# `#10 is fixed but #11 is not fixed` を 2 つの節に分ける。参照の照合は元の本文で行う。
def split_contrast:
  gsub("(?<a>(ました|です|でした|ません)が|けれども|けれど|けど|ものの)(?![、，,])"; "\(.a)\n")
  | gsub("(?i)(?<a>[ \\t])(?<b>but|however|although|whereas)\\b"; "\(.a)\n\(.b)");

# 文字列 $t が指す項目の位置（$its の key）。id か、その項目だけが持つ 20 文字の断片。
# $excl は既定で外した通知の quote_text。通知は項目にならないが、「ほかの項目」には数える（3 回目の直し）。
# 外した通知と同じ文を持つ項目（通知を引用したレビューなど）を、通知の引用で承認しないため。
def refs_in($t; $its; $excl):
  ($t | ascii_downcase) as $raw
  | (norm_text(strip_urls($t))) as $b
  | ($b | windows(20)) as $ws
  | [ range(0; $its | length) as $k
      | $its[$k] as $it
      | ([ $its | to_entries[] | select(.key != $k) | quote_text(.value) ] + $excl) as $others
      | quote_text($it) as $tb
      | select(id_match($raw; (anchor($it.url) | ascii_downcase))
               or any($ws[]; . as $w | ($tb | contains($w)) and all($others[]; contains($w) | not)))
      | $k ];

# 打ち消しの節が触れている項目（id か、URL を外した 20 文字の窓が項目の本文にある。一意でなくてよい）。
def mentions_in($t; $its):
  ($t | ascii_downcase) as $raw
  | (norm_text(strip_urls($t)) | windows(20)) as $ws
  | [ range(0; $its | length) as $k
      | $its[$k] as $it
      | quote_text($it) as $tb
      | select(id_match($raw; (anchor($it.url) | ascii_downcase)) or any($ws[]; . as $w | $tb | contains($w)))
      | $k ];

# 確認（入力の 1 件）が承認する項目の位置の集合。
# 確認の語・打ち消し・参照を読む前に、HTML コメントを本文から除く（4 回目の直し）。見えない語で承認せず、
# ボットの印（`<!-- codex-review-state:v1 {…} -->` など）の中の語で打ち消しにもしない。境界が決まらない
# HTML コメントを持つ確認は、何も承認しない。
def acked_keys($its; $excl):
  if html_comment_ambiguous then [] else
  .body |= ((. // "") | strip_html_comments)
  | [ $its[] | quote_text(.) ] as $texts
  | units as $us
  | attach_targets($us) as $tg
  | [ range(0; $us | length) as $j
      | select($us[$j].type != "block")
      | ($us[$j].text | split_contrast) as $st
      | ($st | clauses(cover_flags($st | ascii_downcase; $texts); url_flags($st)) | map(. + {pol: polarity})) as $cl
      | { j: $j, type: $us[$j].type, cl: $cl,
          pol: (if any($cl[]; .pol == "pos") and any($cl[]; .pol == "neg") then "mixed"
                elif any($cl[]; .pol == "pos") then "pos"
                elif any($cl[]; .pol == "neg") then "neg" else "none" end),
          blocks: [ range(0; $us | length) as $b | select($tg[$b] == $j) | $us[$b].text ] } ] as $segs
  | ($segs | map({key: (.j | tostring), value: .pol}) | from_entries) as $polof
  # 拒否：打ち消しの節が触れた項目と、打ち消しの節を含む単位（neg・mixed）に付いたかたまりが触れた項目。
  | ([ ($segs[] | .cl[] | select(.pol == "neg") | mentions_in(.raw; $its)[]),
       ($segs[] | select(.pol == "neg" or .pol == "mixed") | .blocks[] | mentions_in(.; $its)[]) ] | unique) as $veto
  | [ $segs[]
      | if .pol == "pos" then refs_in(([$us[.j].text] + .blocks) | join("\n"); $its; $excl)[]
        elif .pol == "mixed" then (.cl[] | select(.pol == "pos") | refs_in(.raw; $its; $excl)[])
        elif .pol == "none" and .type == "item" then
          lead_of($us; .j) as $l
          | if $l != null and $polof[$l | tostring] == "pos"
            then refs_in(([$us[.j].text] + .blocks) | join("\n"); $its; $excl)[] else empty end
        else empty end ]
  | unique
  | map(select(. as $k | $veto | index($k) | not))
  end;

def report_author_login:
  (.author.login // "") | sub("\\[bot\\]$"; "");

def is_author:
  (.author.login // "") == ($pr_author // "");

# 既存の ignored_auto_report（著者＋本文パターン）。v1 のまま使う。
def ignored_auto_report_pattern_list:
  $ignored_auto_report_patterns
  | split("\n")
  | map(select(length > 0));

def ignored_auto_report_author_pattern_list:
  $ignored_auto_report_author_patterns
  | split("\n")
  | map(select(length > 0))
  | map(split("\t") as $parts | select($parts | length >= 2) | {
      author: $parts[0],
      pattern: ($parts[1:] | join("\t"))
    });

def ignored_auto_report:
  report_author_login as $author
  | (.body // "") as $body
  | any(ignored_auto_report_pattern_list[]; . as $p | $body | contains($p))
    or any(ignored_auto_report_author_pattern_list[];
           . as $e | $e.author == $author and ($body | contains($e.pattern)));

# 既定で外す自動の通知（3 回目の直し。元帥の決め 2026-11-28）。作者と本文の頭の両方が一致したときだけ外す。
# 片方だけの一致は外さない（迷う入力は赤に倒す）。一覧は jq に固定し、呼び出し側の入力では足しも外しもできない。
# 頭は、取得した本文そのものの先頭で見る（空白・HTML コメント・`>` を飛ばさず、大小文字も区別する）。
# 既存のパターンの `contains`（本文のどこか）とは当て方が違う。
def default_ignored_notices:
  [ { author: "chatgpt-codex-connector", head: "You have reached your Codex usage limits" } ];

def default_ignored_notice:
  report_author_login as $author
  | (.body // "") as $body
  | any(default_ignored_notices[]; . as $n | $n.author == $author and ($body | startswith($n.head)));

# TAKT の失敗報告の種別。本文の語句ではなく、マーカーと著者・本文の形で決める。
# マーカーはフェンスの外にあるときだけ効く（引用ではフェンスの中に入る）。
def has_takt_marker:
  strip_fences
  | test("<!--\\s*takt:auto-report\\s*-->");

# フェンスが 1 つ以上あり、フェンスの外が空白だけ（散文が無い）。
# フェンスの直前に一文だけ散文がある形は、散文があるので自動報告にしない。
def fenced_report_body:
  fence_split
  | .fenced > 0 and (.prose | join("\n") | test("^\\s*$"));

# マーカーは作成者の投稿に限って効く。第三者が付けたマーカーは無視する。
def takt_report:
  is_author and (has_takt_marker or fenced_report_body);

# 自動報告か。v1 の ignored_auto_report（著者＋本文パターン）に、既定で外す通知と
# TAKT の失敗報告の種別を足す。それ以外の項目の選び方は変えない。
def is_auto_report:
  ignored_auto_report or default_ignored_notice or takt_report;

# Codex の承知。v1 と同じく文頭一致だけを見る。語彙も v1 と同じ trusted_ack_words だけ。
# 本文の途中の `fixed` も、文頭の `Fixed` も承知にしない（Codex の要約を項目から消さない）。
def trusted_acknowledgement:
  report_author_login == "chatgpt-codex-connector" and ack_at_start;

def is_item:
  (trusted_acknowledgement | not)
  and ((.author.login // "") != $pr_author)
  and (
    $pr_author_type != "Bot"
    or (
      .authorAssociation != "OWNER"
      and .authorAssociation != "MEMBER"
      and .authorAssociation != "COLLABORATOR"
    )
  );

def is_acknowledger:
  (.author.login // "") == $pr_author
  or trusted_acknowledgement
  or (
    $pr_author_type == "Bot"
    and (
      .authorAssociation == "OWNER"
      or .authorAssociation == "MEMBER"
      or .authorAssociation == "COLLABORATOR"
    )
  );

# 判定の順序: 先に自動報告を外し、残った候補だけで項目と承認を数える。
# 自動報告は is_item にも is_acknowledger にも入らない（acked_keys より前）。
# 確認ごとに、承認する項目の位置（$its の key）を acked_keys で求め、対象の最終編集より後のものだけを数える。
$items as $all
| ($all | map(select(is_auto_report))) as $reports
| ($all - $reports) as $candidates
| ($candidates | map(select(is_item))) as $its
| ($reports | map(select(default_ignored_notice) | quote_text(.))) as $excl
| [ $candidates[] | select(is_acknowledger) | {at: .createdAt, keys: acked_keys($its; $excl)} ] as $acks
| [ range(0; $its | length) as $k
    | $its[$k] as $item
    | select([ $acks[]
               | select(.at > ($item.updatedAt // $item.createdAt))
               | select(.keys | index($k) != null) ] | length == 0)
    | $item
  ]
````

「ほかの項目」は位置（`key`）で分けるので、本文が同じ 2 つの項目（同じボットの通知が 2 回など）は、互いの断片を「ほかの項目にある」とみなし、引用ではどちらも承認できない。それぞれの URL を貼る。既定で外した通知の本文（`$excl`）も「ほかの項目」に足す。

`is_item` と `is_acknowledger` は v1 の `select` を分けただけである（自動報告の除外は `is_item` の中ではなく、その手前の `$candidates` で済ませる）。この順序なので、自動報告に対して `acked_keys` は評価されない。また、**項目選別の中では `trusted_acknowledgement`（文頭一致）だけを見る**。確認の語（`acked_keys` の単位ごとの語）は承認の判定で評価する。`trusted_acknowledgement` は v1 と同じく `^\s*` の文頭一致で、**本文の途中に `fixed` があっても承知にしない**（v1 で赤だった Codex の要約を、項目から消して緑にしない）。`trusted_acknowledgement` は「Codex のコメントを項目から外す」ためと、Codex を承認の候補にするために使い、**ほかの項目の承認としては、上の 4 と 5 を満たすときだけ**数える。これで「Codex の 1 つの `Acknowledged.` が全項目を承認する」穴も塞がる。語彙は **v1 と同じ狭い一覧**（`acknowledged` / `addressed` / `確認しました` / `承知しました` / `了解しました` / `対応済み` / `対応しました` / `対処しました`）だけを使う。4 回目に広げた `Fixed`・`確認済み`・`修正しました`・`直しました`・`確認いたしました`・`対応いたしました` は、**著者自身の確認（条件 4）の `ack_words` にだけ**使い、Codex の承知には使わない。これで Codex の要約が `Fixed …` や `確認済みです。ただし…` で始まっても項目から消えず、v1 と同じ赤になる。文頭に来たときだけ承知なので、`確認しました` が文頭にあれば項目から外れ、本文の途中なら項目として残る。`is_auto_report` は v1 の `ignored_auto_report` に既定の通知（作者と本文の頭の両方）と TAKT の種別判定を足しただけなので、Codex の明示の確認は自動報告に落ちない（`Acknowledged` などで始まる本文は通知の頭で始まらない）。

### jq の版と、位置に頼らない判定（3 回目の直し）

d7e6d5b の `id_match` は `indices` で一致の位置を取り、その直後の 1 文字が数字かを見ていた。jq 1.7 までの `indices` は文字列の位置をバイトで返す（コードポイントで返すのは jq 1.8.0 から。jqlang/jq#3065）。そのため日本語の後ろでは「直後の 1 文字」がずれ、id の一致が誤って偽の緑になる。例：`id_match("確認しました #issuecomment-101"; "#issuecomment-10")` は、jq 1.6 と jq 1.7 で `indices` が `[19]`（コードポイントでは 7）を返して true になる。jq 1.8.1 では `[7]` で false。

元帥の決めは「1.7 未満なら失敗」だったが、PR #456 のレビュー（Cursor Bugbot）で jq 1.7 も同じだと分かり、実物で確かめた。GitHub のランナーの系の jq（ubuntu:24.04 の apt。`jq --version` は `jq-1.7`）も `[19]` を返す。そこで中将の判断（2026-11-28）で、**下限は 1.7 のまま、`id_match` を位置を使わない形に書き直す**ことにした（根の直し）。下限を 1.8 に上げて jq を固定して入れる案は採らない（22 リポジトリのワークフローに段が要り、根の直しで足りるため）。

- **`id_match`**：`indices` をやめ、正規表現の先読みで決める（`test(<アンカーをエスケープしたもの> + "(?![0-9])")`。判定の式の `re_escape` と `id_match`）。位置を一切使わないので、jq の版によらない。
- **ほかに位置に頼る所**（判定の式を洗い出した）：`windows`（`length` と文字列の切り出し `$s[$i:$i+$n]`）、`negated2`・`pending_hits`（`match` の `offset` と切り出し）、`cover_flags`（`explode | length` と切り出し）、`clauses`・`backtick_runs`（`explode` したコードポイントの配列）。`index` は配列（`$veto`、`.keys`）にだけ使っている。jq 1.6・1.7・1.8.1 で、`match` の `offset`（7）、切り出し（`$r[7:9]` が `#i`）、`length`（24）、`explode | length`（24）がどれもコードポイントで数えることを確かめた。文字列に `indices`・`index`・`rindex` を使う所は、`id_match` のほかに無い。4 回目の直しで足した `url_flags` も、`explode` したコードポイントの配列を比べるだけで、位置を `indices` で取らない（`blank_urls` は URL を同じ数の空白に置き換えるので、元の本文と同じ長さになる）。**方針：文字列の位置は `match` の `offset` か `explode` で取り、文字列に `indices`・`index`・`rindex` を使わない。** 実装でもこの方針を守る。
- **構文**：2 回目の直しの `backtick_runs` は、オブジェクトの値に括弧の無い引き算（`len: (…) - $i`）を書いていて、jq 1.6・1.7 では構文の誤りで動かなかった（jq 1.8 で許された書き方）。括弧で囲んだ（`len: ((…) - $i)`）。
- **確かめ**（2026-11-28、docker の ubuntu:22.04 の jq 1.6、ubuntu:24.04 の jq 1.7、ubuntu:24.04 に入れた jq 1.8.1）：この文書の jq を切り出して、3 つの版で同じ結果になった。25〜29 の 55 行は表どおり、30〜33 の 18 例はすべて期待どおり。書き直した `id_match` は 3 つの版で上の例が false（`#issuecomment-10。` には true、`#issuecomment-1` には false）。d7e6d5b の jq（構文だけ同じ括弧で直したもの）は、jq 1.6・1.7 で `確認しました #issuecomment-101` が `#issuecomment-10` の項目を承認する（偽の緑）。jq 1.6 でも同じ結果になったが、下限は決めのとおり 1.7 に置く（確かめた範囲を版で限るため）。

そのうえで、`filter_unacknowledged_comments` の頭で jq の版を確かめ、1.7 未満なら失敗にする。

```bash
require_jq_17() {
  local v
  v="$(jq --version 2>/dev/null || true)"
  if [[ ! "$v" =~ ^jq-([0-9]+)\.([0-9]+) ]]; then
    echo "::error::jq の版を読めません（'${v}'）。jq 1.7 以上が要ります。" >&2
    return 1
  fi
  if (( BASH_REMATCH[1] < 1 || (BASH_REMATCH[1] == 1 && BASH_REMATCH[2] < 7) )); then
    echo "::error::jq ${v#jq-} では判定できません。jq 1.7 以上が要ります。" >&2
    return 1
  fi
}
```

- 版の文字列が `jq-<数>.<数>` で始まらない（読めない）ときも失敗にする（迷う入力は赤に倒す）。`jq-1.6`・空・`jq version 1.7` は失敗、`jq-1.7`・`jq-1.7.1`・`jq-1.8.2` は通ることを、偽の `jq` で確かめた。
- 知らせは標準エラーに出す（`filter_unacknowledged_comments` の標準出力は `unacknowledged="$(…)"` に取り込まれるので、標準出力に出すとログに残らない）。失敗は `return 1` で返し、`check_pr` が `error` のステータスを公開する経路（v1 の #39 と同じ）に乗せる。判定を飛ばして成功にしない。`main` の頭で止めると、ステータスを公開しないまま終わり、同じ head に前の評価の `success` が残りうる。そのため `ERROR_STATUS_SHA` が決まったあとの判定の入口に置く。
- 再利用ワークフローは `ubuntu-latest`（いまは ubuntu-24.04）で動く。ubuntu:24.04 の apt の jq（`jq-1.7`）で判定が通ることは docker で確かめた。GitHub のランナーそのものの jq は 1.8.1 だった（j5ik2o/ci#43 の 77ccaac の CI で、スモークの頭に出した `jq --version`）。ubuntu-22.04 や自前のランナーで jq 1.6 のときは、関門が error になる。
- **CI で 2 つの jq で流す**（4 回目の直し。中将の決め、2026-11-28）。関門の下限は 1.7 だが、ランナーの jq は 1.8.1 なので、CI のスモークは 1.7 で流れていない。jq 1.8.0 から `indices` の数え方が変わったように、版で振る舞いが変わる所は 1.7 でしか見えない。そこで j5ik2o/ci の `.github/workflows/validate.yml` に、次の 2 つでスモーク（`tests/review-thread-resolution-smoke.sh`）を流す段を置く。実装はこの文書の範囲の外で、j5ik2o/ci の実装の PR で入れる。
  - **ubuntu-latest の jq**：いまの `Review-thread smoke tests` の段のまま（`runs-on: ubuntu-latest`）。スモークの頭で `jq --version` を出す（77ccaac で入れた）。
  - **jq 1.7**：同じ job に段を足すか、別の job（`runs-on: ubuntu-latest`）を足し、`bash tests/review-thread-resolution-smoke-jq.sh 1.7` を流す（77ccaac で入れた道具。docker の ubuntu:24.04 の apt の jq で、リポジトリを読み取り専用で渡す）。docker の取得と apt の分だけ時間が延びるので、別の job にして並べるのがよい（validate の job の `timeout-minutes: 10` に収める必要が無い）。
  - どちらかが落ちれば Validate を赤にする。jq 1.6 で版の確かめが効くこと（`… -jq.sh 1.6`）は、CI に入れなくてよい（版の確かめの段の固定例は、偽の `jq --version` で観点 32(b) が見る）。

### 赤のときの案内

いまの `build_summary` は未承認の項目を列挙するだけで、解消の仕方を書いていない。次を足す。

```text
### 未承認のトップレベルコメント／レビュー要約
- by <author> updated at <time>: <url>
  確認するには、返信にこの URL を含めるか、本文を 20 文字以上引用し、
  「確認しました」などの語を添えてください（URL は長さを問いません）。
  引用はコードフェンスで囲んでもかまいません。
  ほかの項目にもある文（定型文）と、URL の一部は引用として数えません。
  確認の語は、URL・引用と同じ段落かリストの項目に書いてください。
  引用（行頭の >、「」）の中の語と、「未対応です」「not been fixed」
  「確認済みではありません」のような打ち消しは確認として数えません。
  HTML コメント（<!-- -->）の中に書いた語と URL は読みません。
  URL の中の語（リポジトリ名の fixed・pending など）は、確認にも打ち消しにも数えません。
  閉じない <!-- や、コードの中の <!-- を含む返信は確認になりません。

同じ文が並ぶ自動の通知（レート制限の通知が 2 回など）は、引用ではどれも確認になりません。
通知ごとに URL（アンカー）を貼り、同じ行に確認の語を添えてください。
  例: - https://github.com/o/r/pull/1#issuecomment-1001 を確認しました。
      - https://github.com/o/r/pull/1#issuecomment-1002 を確認しました。

自動投稿（TAKT の失敗報告など）は確認として数えません。
```

URL をそのまま貼れるので、人が迷わない。HTML コメントの 2 行は 4 回目の直しで足した。Codex の利用上限の通知は既定で外れて項目にならないので、案内にはその書き方を書かない（3 回目の直し）。同じ文が並ぶ通知の案内は、既定で外れない自動の通知（CodeRabbit のレート制限など）のためである。TAKT の失敗報告は種別で外れるので、失敗報告に確認の語を入れないという規約は要らない（後述）。

### 変えないこと

- 未解決スレッドの判定（`isResolved`）は変えない。スレッドの返信は承認ではなく、解決（resolve）だけが関門を外す。
- ステータスの context 名（`Check unresolved comments`）、公開方法、branch protection / ruleset は変えない。
- GitHub API の呼び出しは増やさない。コメントとレビューはすでに取得しており、判定は手元の jq だけで完結する。
- 自動投稿として外す対象（CodeRabbit の要約、Codex の要約、TAKT の失敗報告など）は、Codex の利用上限の通知を既定に足すほかは変えない。既存の `ignored_auto_report`（著者＋本文パターン）もそのまま使う。変えるのは当て方の一部で、TAKT の失敗報告は文面パターンではなく種別（フェンスの外の `<!-- takt:auto-report -->`、または著者が作成者で本文がフェンスだけ）で外す（「判定の順序」）。
- Codex の利用上限の通知は、既存のパターン一覧（入力で上書きできる `ignored_auto_report_author_patterns`）には入れず、jq に固定した既定の除外として足す（3 回目の直し。「Codex の利用上限の通知を既定で外す」）。再利用ワークフローの inputs は変えない。

## 適用と移行

### v2 を切る（採用）

`v1` はそのまま残し、`v2` を新しく切って、リポジトリごとに `uses` と `ci_ref` を v2 に上げる。

| 観点 | v1 を直接書き換える | v2 を切る（採用） |
| --- | --- | --- |
| 影響範囲 | 22 リポジトリの次のイベントで一斉に変わる | 上げたリポジトリから順に変わる |
| 観察 | できない。全 PR が同時に新判定になる | 砂場と takt-dash で先に観察できる |
| 誤って赤にしたとき | 全リポジトリのマージが止まる。戻すには v1 を付け替える（全体操作） | そのリポジトリの 2 行を戻すだけ。次回の評価で戻る |
| 監査 | タグを付け替えた事実が残らず、どの判定がいつからか読めない | `v2` のコミットが固定で読める |
| コスト | 変更 1 回 | 22 の小さな PR（各 2 行）。まとめて自動化できる |
| 既存の緑 | 予告なく判定が変わる | 変わるのは上げたリポジトリだけ |

v1 を直さない理由は、22 のすべてが `Check unresolved comments` を必須にしており、判定の誤りがそのままマージ停止になるためである。とくに TAKT の自動 PR は、失敗報告が承認に数えられなくなると赤のまま止まる。砂場で先に確かめられない一斉変更は、この関門には重すぎる。

### タグの扱い

- `v2` は切ったら動かさない（force-push で付け替えない）。どのリポジトリがどの判定で走ったかを後から読めるようにする。
- 直すときは `v2.1` を切る（`v2` は残す）。影響するリポジトリだけ `uses` と `ci_ref` を `v2.1` に上げる（2 行は同じ PR で変える）。
- `v1` は削除しない。SHA 固定の逃げ道として `2ead62a` を README に書く。

### タグを切る条件

`v2` は、点検で見つかった次の 5 件が直るまで切らない。どれも、切ったあとに見つかると `v2.1` を切って全リポジトリを上げ直すことになる。

- [j5ik2o/ci#44](https://github.com/j5ik2o/ci/issues/44)：断片の照合が URL の共通の頭に当たる。この設計の条件 5（URL を外す、ほかの項目にある断片を使わない）を実装し、スモークテストの反例（いまは `got 0 / success`）が赤になること。
- [#443](https://github.com/j5ik2o/takt-dash/issues/443)：Quint のモデルが承認の判定を計算していない。`specs/quint/review-thread-ack/` で直した（「Quint の要否」）。takt-dash の main に入ること。
- [j5ik2o/ci#45](https://github.com/j5ik2o/ci/issues/45)：スモーク 18a が #131 の実物の形（本文全体が ```text のフェンス）でない。テストの観点 18 の形の固定例が入ること。
- [j5ik2o/ci#43](https://github.com/j5ik2o/ci/pull/43) のレビューの残る穴 4 つ（まとめ返信の効く範囲、引用の中の語、英語の否定、日本語の否定）：「確認の語の効く範囲と打ち消し」を実装し、テストの観点 25〜29 の表の行が、b808a29 の列では誤った承認、この規則の列のとおりに固定されること。
- j5ik2o/ci#43 の 77ccaac のテストで見つかった 06770ed の穴（HTML コメントの中の語、URL の中の語。穴 5〜7）：「HTML コメントと URL の中の語」を実装し、テストの観点 34・35 の表の行が、この規則の列のとおりに固定されること。validate のワークフローで、jq 1.7 と ubuntu-latest の jq の 2 つでスモークが通ること（「jq の版と、位置に頼らない判定」の CI の段）。

**新旧の比較（「移行の順」2）で差が 0 件でも、ci#44 の穴は見つからない。** v1 は対象より後ろの作成者のコメントを内容によらず承認にするので、ci#43 の規則が URL の頭で承認する項目は、v1 でも必ず承認になる。新旧がどちらも緑の偽の緑は、差には出ない（旧の判定に、内容で承認を決める経路が無い）。偽の緑は、新しい判定だけを見て、各項目が**どの経路で承認されたか**を確かめないと見つからない。2026-11-27 の「差 0 件」もこの穴を見ていない。

### 呼び出し側の変更（各リポジトリ 2 行）

```yaml
uses: j5ik2o/ci/.github/workflows/review-thread-resolution.yml@v2
...
ci_ref: v2
```

- 2 行は**同じ PR** で変える。`uses` だけ v2 にして `ci_ref: v1` のままだと、v2 のワークフローが v1 のスクリプトを checkout し、**古い判定のまま黙って動く**。`ci_ref` だけ v2 にすると、v1 のワークフローが v2 のスクリプトを動かす。どちらも避ける。

27. **英語の否定（穴 3）。** 同じ節の前の否定・条件・未来で、英語の語を数えない。`This has not been fixed.`（Devin の例）、`hasn't been fixed yet`、`isn't fixed`、`was not actually addressed`、`will be fixed in a follow-up`、`Once this is fixed` は通らない。`Fixed #10 in abc123.`、`Not a bug, but fixed`、`No regressions; fixed`、`should be fixed now` は通る。日本語の語には当てない（`Action not completed を確認しました` は通る）。誤って赤にする形 `doesn't affect X and is fixed` も固定する（赤）。

## 影響と戻し方

### 影響するリポジトリ（2026-11-27 時点）

上の 22 リポジトリ。すべてで `Check unresolved comments` が必須。v2 に上げたリポジトリは、次の評価から新しい判定になる。

- 既存の open PR で、内容によらない作成者コメントだけに頼って緑だったものは、赤に戻る可能性がある。2026-11-27 の 15 件では 0 件だった。2 回目の直し（確認の語の効く範囲を単位に限る）のあとの規則では `event-store-adapter-java#871` が赤になり、マージ済みの modern-ddd-book#695 も評価し直せば赤になった（Codex の利用上限の通知を指す単位に確認の語が無い）。3 回目の直しで、この通知は既定で外れて項目にならないので、2 件とも緑に戻る（2026-11-28 に測り直した）。
- 新しく赤になった PR は、作成者が URL（長さを問わない）か 20 文字以上の引用に「確認しました」を添えて返信すれば緑になる。関門の要約にその案内を出す。引用は、その項目だけが持つ文（URL の外）でなければ数えない。同じ文の項目が複数ある PR（同じレート制限の通知が 2 回、同じ見出しの要約が 2 つ）では、引用の代わりにそれぞれの URL を貼る運用になる。
- 利用者ごとの運用（「一意に指す値として何を使うか」の実測）：
  - takt-dash、dotfiles：確認は URL を含まず、引用か記録の形。引用がその項目に固有なら、そのまま通る。TAKT の窓口が書いていた Codex の利用上限の通知への確認（`Codex（…）の「You have reached …」を確認しました`）は、v2 では通知が既定で外れるので要らなくなる。
  - pekko-persistence-dynamodb、event-store-adapter-kotlin：確認に run や compare の URL、接頭辞の無い id（`comment6767269753`）を含むことがある。これらは承認の経路にならないので、項目のアンカーを貼るか、URL の外の文を引用する形に変える。ci#43 の規則のまま v2 を切っていれば、この形が URL の頭で黙って通っていた。
  - modern-ddd-book：Codex の利用上限の通知を呼び出し側で外していなかった。v2 では既定で外れるので、通知への返信は要らなくなる。
  - 5 つとも、v1 のあいだは何も変わらない。v2 に上げる PR の本文に、確認の書き方（「一意に指す値として何を使うか」の例）を貼る。
- TAKT の失敗報告は、種別（フェンスの外の `<!-- takt:auto-report -->`、または著者が作成者で本文がフェンスだけ）で自動報告として外れるので承認に数えられない。TAKT が失敗報告を投稿しても、関門は赤のまま人を待つ。これは #134 の意図どおりである。失敗報告に確認の語を入れない規約は要らなくなった。代わりに、散文を伴う報告（フェンスの直前に一文だけ置く形を含む）にするときは `<!-- takt:auto-report -->` を付ける必要がある（別 PR、未確認）。
- Codex の利用上限の通知は、v2 に上げたリポジトリでは既定で外れて項目にならない（緑）。承認にも数えない。v1 のままのリポジトリでは、呼び出し側の除外が無ければ未承認の項目として残り、作成者の返信で通す。Codex のほかのコメント（本物のレビュー・要約・指摘）の扱いは変わらない。

「適用と移行」の表のとおり。もっとも速いのは、そのリポジトリの 2 行を v1 に戻すこと。`v2` の付け替えはしない（`v2` は切ったら動かさない）。全体に効く不具合でも、各リポジトリを v1（または `2ead62a`）に戻し、修正は `v2.1` として切ってから、必要なリポジトリだけ上げる。

## 守る不変条件

- I1（緑の意味）：関門が緑になるのは、未解決スレッドが 0 件で、かつすべての未承認項目に有効な承認があるときだけ。
- I2（#134 の修正）：作成者が自分の文で書いた打ち消されない確認の語と、対象を一意に指す値（対象の id、または URL を外した本文で対象だけが持つ 20 文字以上の断片）が**同じ単位**にある確認だけが、その対象を承認する。同じ確認の打ち消しの節が対象に触れていれば承認しない。引用の中の語、打ち消された語（英語・日本語）、「まだ」の表明は確認の語にならない（2 回目の直し）。HTML コメントの中の語と参照は読まず、URL の中の語は確認の語にも打ち消しにもならない。境界が決まらない HTML コメントを持つ確認は、どの項目も承認しない（4 回目の直し）。確認の語も対象への参照も無い作成者コメントは、決して承認にならない。**対象を指さない確認は、どの項目も承認しない**：別件の URL（URL の共通の頭 `https://github.com/j` だけが一致する。[j5ik2o/ci#44](https://github.com/j5ik2o/ci/issues/44)）や、ほかの項目にもある定型文の引用では承認にならず、1 つの確認が指していない項目を承認することもない（[#443](https://github.com/j5ik2o/takt-dash/issues/443)）。Quint の `noFalseGreen` が、この性質を作成者の意図と突き合わせて確かめる。
- I3（自動報告）：自動報告（既知の自動投稿、作者が Codex で本文が利用上限の通知の頭で始まる投稿、著者が作成者でフェンスの外に `<!-- takt:auto-report -->` を持つ投稿、著者が作成者で本文がフェンスだけの TAKT の失敗報告）は、項目にも承認の候補にもならない。Codex の利用上限の通知は、作者と頭の両方が一致したときだけ自動報告とし、片方だけなら項目に残る（3 回目の直し）。確認の語や引用を含んでいても承認にならない。TAKT の失敗報告かどうかは著者と種別で決め、本文の語句では決めない。第三者が付けたマーカーは種別と認めない（他人のマーカーで項目を消したり緑にしたりできない）。第三者が付けたマーカー付きのコメントは、自動報告にせず**未承認の項目として残る**。
- I4（順序）：対象の最終編集より前のコメントは承認にならない。承認のあとで対象が編集されたら、承認し直しが必要。
- I5（純関数）：判定は取得済みのコメントとレビューの集合だけで決まる。実行順、並行性、リトライ、ページ取得の順に依存しない。同じ入力なら同じ結論。
- I6（正当な確認）：対象の URL / アンカーと確認の語（URL・アンカーは長さを問わない）、または対象だけが持つ 20 文字以上の引用と確認の語が同じ単位にそろい、同じ確認の打ち消しの節が対象に触れていなければ、緑になる。打ち消しの語が URL かボットの印（HTML コメント）の中にだけあっても、緑になる（4 回目の直し）。
- I7（API 不増）：判定のために新しい GitHub API 呼び出しをしない。
- I8（設定不変）：ステータスの context 名と公開方法を変えない。branch protection / ruleset を触らない。

## Quint の要否

**書く。** ただし、関門の実行そのもの（API 呼び出し、リトライ、並行実行）の状態機械ではなく、承認の判定が赤と緑の間を動く部分だけの最小モデルである。

理由は、#134 が「緑に到達できてしまう」という到達性の問題であり、コメントの投稿・編集の並びに対して、v1 の判定と提案の判定がどこで分かれるかを反例として出せるからである。とくに「対象が編集されると承認が無効になり、緑から赤へ戻る」遷移がある。状態が無い純関数ではあるが、入力の並びに対する関門の結論の遷移はある。

モデルは [`specs/quint/review-thread-ack/`](../../specs/quint/review-thread-ack/README.md) に置いた（`reviewThreadAck.qnt` と `reviewThreadAck_test.qnt`、`ci-specs.json` に登録済みで、CI の `quint` ジョブが流す）。

### 前の下書きの穴（#443）

前の下書き（この文書に直接書いていたもの）は、確認を投稿する時点で `{ item: ItemId, kind: AckKind }` と項目に結び付け、STRICT のとき `implementedAck` を仕様の `isStrictAck` そのものにしていた。そのため `noFalseGreen`（`gateGreen implies allStrictAcked`）は恒真で、strict の「違反なし」は何も確かめていなかった。また、確認がどの項目を承認するかをモデルが計算しないので、「1 つの確認で全項目が通る」形も、ci#44 の「URL の頭だけの一致」も表せなかった。点検は、これが ci#43 の URL の穴を見逃した理由の 1 つと見ている（[#443](https://github.com/j5ik2o/takt-dash/issues/443)）。

### 直したモデル

- 確認は投稿の時点ではどの項目にも結び付けない。確認が持つのは、本文から観測できるもの（承認できる人か、自動報告か、1 つか 2 つの**単位**）と、作成者が承認するつもりだった項目（`intended`）・「まだ」と書いた項目（`pending`）である。単位は、確認の語の現れ方（`Word`）、含むコメントの id、含む断片を持つ（2 回目の直し）。
- `Word` は、文字列の水準の分類（jq の `clauses` と `polarity`）の結果を観測として与える。`Affirmed`（作成者が自分の文で書いた打ち消されない語）、`Quoted`（語が引用・項目の写しの中にだけある。穴 2）、`NegatedEn`（助動詞を挟む英語の否定。穴 3）、`NegatedJa`（後ろに付く日本語の否定。穴 4）、`Pending`（語が無く「まだ」と書く）、`NoWord`、`MaskedWord`（語が URL か HTML コメントの中だけ。穴 5・7）、`AffirmedMaskedCue`（作成者の語があり、打ち消しの語は URL か HTML コメントの中だけ。穴 6）の 8 つ（最後の 2 つは 4 回目の直し）。仕様と環境の前提は、作成者の語の単位（`Affirmed` と `AffirmedMaskedCue`）を規則の `polarity` を使わずに `authorWord` で読む。どの文字列がどの `Word` になるかの正しさは、モデルでは確かめない（テストの観点 25〜29 の表で確かめる）。
- 項目の本文は 20 文字以上の断片の集合に畳む。`Own(i)` は項目 i だけが持つ散文、`Shared` は複数の項目に現れうる定型文、`UrlHead` は URL の頭（`https://github.com/j`）。どの項目が `Shared` と `UrlHead` を持つかは初期状態で非決定に選ぶ。
- 規則は定数 `RULE` で切り替える。`v1`（いまの v1）、`window`（ci#43 の 442d679・86a443c の 20 文字の窓）、`unique`（b808a29。語と参照を本文の全体で見て、`Quoted`・`NegatedEn`・`NegatedJa` も確認と数える）、`scoped`（この設計の 2 回目の直し）。`scoped` は、極性 `polarity` が `Pos` の単位の中で語と一意の参照がそろい、`Neg` の単位がその項目に触れていないときだけ承認する。規則は `intended`・`pending` を読まず、**どの確認がどの項目を承認するかを計算する**。
- 仕様 `noFalseGreen` は、関門が緑なら、すべての項目に「その項目を承認するつもりで、最後の編集より後に書かれた、自動報告でない、作成者が自分の文で語を書いた確認」があることを求める。仕様は `intended` と編集の記録 `editLog` を読み、規則が読む `updatedAt` とは別の経路で最後の編集を求める。前の下書きのように仕様と規則が同じ定義を共有すると、規則を壊しても仕様が一緒に動いて違反が出ない。同じ理由で、環境の前提（`consistent`・`pendingOk`）は規則の `polarity` を使わず、`Word` を直接読む。`idAckTurnsGreen`（I6）は、すべての項目に、id を確認の語と同じ単位に含み、打ち消しの単位がその項目に触れていない有効な確認があれば緑であることを求める。
- 項目に真の種類（`Kind`：`Plain`・`CodexNotice`・`CodexOther`・`HeadByOther`）と、規則が読む 2 つの観測（作者が Codex か `byCodex`、本文が通知の頭で始まるか `noticeHead`）を持たせた（3 回目の直し）。観測は種類から決まり（作者が Codex で頭で始まるのは通知だけ、という環境の前提）、`scoped` は両方が真の項目だけを外す（`defaultExcluded`）。仕様（`noFalseGreen`・`idAckTurnsGreen`）は規則の `defaultExcluded` を使わず、種類が `CodexNotice` の項目だけを承認を待たない項目とする。外した項目の断片は、`uniqueTo` の「ほかの項目」に数えたまま（jq の `$excl`）。`legacy`・`window`・`unique` には既定の除外が無い（通知も項目のまま）。
- 確認の本文に何が現れうるかには前提を置く（`consistent`・`pendingOk`）。`Affirmed` の単位の id と固有の散文は、承認するつもりの項目か、同じ確認で「まだ」と書いた項目のもの。打ち消しの単位（`NegatedEn`・`NegatedJa`・`Pending`）の id と固有の散文は、「まだ」と書いた項目のもの。「まだ」と書いた項目は承認するつもりの項目ではない。定型文は、それを持つ項目がある PR にしか現れない。`Quoted` と `NoWord` の単位の id と断片、どの単位の URL の頭も、意図と無関係に現れる（指摘を引用して質問する、別件として触れる）。この前提を外すと `fixed` でも反例が出るので、結論はこの前提に依存する。前提が崩れる入力（別の PR の項目の文を偶然 20 文字以上写すなど）は、モデルの範囲外である。
