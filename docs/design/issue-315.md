## 指摘ごとの変更

### D4：マージの操作の呼び名を「マージする」の 1 つにする

backend の ApproveGoalMerge は、takt の `takt_merge_goal_pr` でマージのタスクを依頼し、タスク名を返すだけです（`backend/src/grpc/writes.rs:133-169`）。応答の時点ではプルリクエストはまだマージされていません。そのため成功の文は、issue の案の「PR #N をマージしました。」ではなく「PR #N のマージを依頼しました。」にします。

| 場所 | いまの文言 | 直した後の文言 |
| --- | --- | --- |
| 一覧のボタン（`confirm-dialog.tsx:279`） | `マージを承認` | `マージする` |
| ダイアログの見出し（`:310`） | `マージの承認` | `プルリクエストのマージ` |
| ダイアログの本文（`:315`） | `プルリクエスト #418 のマージを承認します。よろしいですか。` | `プルリクエスト #418 をマージします。よろしいですか。` |
| 確定ボタン（`:316`） | `マージする` | `マージする`（変えない） |
| 成功の文（`decision-actions.ts:212` の `SUCCESS_MESSAGES.merge`） | `マージを承認しました。` | `PR #418 のマージを依頼しました。` |
| 操作できない理由（`decision-action-builders.ts:41, 44, 49`） | `…ため、マージを承認できません。` | `…ため、マージできません。` |

- 理由：同じ操作に「承認」と「マージする」の 2 つの呼び名がある。成功の文は、backend が実際にしたこと（マージの依頼）と合わせる。
- 見出しは確定ボタンと同じ文にしない（既存の契約。ダイアログの読み上げ名と確定ボタン名が重ならない）。
- 成功の文の PR 番号は、送った操作の `payload.prNumber` から作る。
- 一覧のボタンと確定ボタンが同じ名前になる。ダイアログは `aria-modal="true"` なので読み上げでは区別できる。e2e で項目の中から一覧のボタンを探すときは、文書の順で先にある方（`.first()`）を使う。
- テストで固定すること：
  - 判断待ち一覧のマージ待ちの項目のボタンの名前が `マージする`。`マージを承認` の文が判断待ちの画面のどこにも出ない。
  - 開いたダイアログの h2 が `プルリクエストのマージ`、本文が `プルリクエスト #418 をマージします。よろしいですか。`、確定ボタンが `マージする`。
  - `submitDecisionAction(buildMergeAction(マージ待ち))` が成功したときの文が `PR #418 のマージを依頼しました。`。成功の文を出しているのは `src/state/decision-actions.ts` の `SUCCESS_MESSAGES` と `submitDecisionAction` なので、その関数のテスト `test/state/decision-actions.test.ts` の「マージ・ゴール登録の承認と却下も種類ごとの Route Handler へ送る」で固定する（main の同じテストは `マージを承認しました。` を固定している。このブランチで書き換え、いまの main では落ちる）。`test/pages/issue-315-wording.test.ts` にも同じ確かめを置く。
  - 結果の表示（`DecisionResults`）は `result.message` をそのまま出すだけなので、文面は state の側だけで決まる。e2e で成功の文を文字で固定しているのは `回答を送信しました。`（`flow-3-decisions-answer`、`flow-8-write-failure-recovery`、`issue-308-operation-confirm`）だけで、この文は変えない。マージの成功の文を固定した e2e は無い。
  - URL・番号・ゴール ID が欠けたマージ待ちの理由の文が `…ため、マージできません。`。

### D6：確定ボタンを「やめる」と見分けられる色にする

- いま：ダイアログの「やめる」と確定ボタンは、どちらも `.actions button`（白地に灰色の線）で、見た目が同じ。
- 直した後：ダイアログの確定ボタン（マージする・ゴール登録を承認する・ゴール登録を却下する、#404 で入った作業の依頼の `実施した`・`対応できない`）に `class="danger"` を付ける。`.actions button.danger` は地色を `var(--orange-d)`、文字色を白（`#fff`）、線を `var(--orange-d)` にする。
- hover と無効は、セレクタの詳細度で既存の規則に負けないよう、明示する：
  - `.actions button:hover:not(:disabled)`（`globals.css:1177-1180`）は `.actions button.danger` より詳細度が高く、そのままでは hover で文字が teal（`--accent`）になり、白地でない地色の上で読めなくなる。`.actions button.danger:hover:not(:disabled)` を足し、地色・文字色を danger のまま（地色 `var(--orange-d)`、文字色 `#fff`）にする。線の色だけ変えてよい。
  - `.actions button:disabled`（`:1182-1185`）は文字色だけを変えるので、danger の無効は橙の地色のまま押せる見た目に残る。`.actions button.danger:disabled` を足し、地色を `var(--surface)`、文字色を `var(--down)`、線を `var(--line)` にする（ほかの無効のボタンと同じ見た目）。
- 理由：5 つの確定はどれも画面から取り消せない書き込みです。「やめる」と同じ見た目だと、押し間違いに気づけない。赤のトークンは無いので、警告に使っている `--orange-d` を使う（白との比は 4.5:1 以上）。
- 一覧のボタン（ダイアログを開くだけ）には付けない。開くだけでは書き込まない。
- テストで固定すること：
  - 5 種のダイアログ（マージ、ゴール登録の承認・却下、作業の依頼の実施した・対応できない）で、確定ボタンが `danger` のクラスを持ち、「やめる」は持たない。一覧のボタン（開くだけ）は持たない。
  - `globals.css` の `.actions button.danger` の地色が `--surface` ではない `var(--…)` で、文字色との比が 4.5:1 以上。
  - `.actions button.danger:hover:not(:disabled)` に地色と文字色があり、文字色が `var(--accent)` ではなく、比が 4.5:1 以上。
  - `.actions button.danger:disabled` の地色が `var(--surface)`、文字色が `.actions button:disabled` と同じ `var(--down)`。

### D7：操作の結果に時刻を付け、「閉じる」で利用者が片づける

元帥の決定（案 A）：結果の表示に「閉じる」のボタンを付ける。自動では消さない。

- いま：結果は項目ごとに 1 件ずつ一覧の上に溜まり、時刻が無いので、どれがいつの結果か分からない。消す手段も無い。
- 直した後：
  - `DecisionResult` に、結果が出た時刻 `at: Date` を足す。`toDecisionResult(decision, outcome, at = new Date())` の 3 つ目の引数は省略できる（いまの 2 引数の呼び方はそのまま通る）。結果の 1 行に `<time dateTime="<ISO 8601>">HH:MM</time>` を出す（`formatClock`）。並びは、いまと同じく新しい結果が先頭。同じ項目の結果は、いまと同じく置き換える（`upsertDecisionResult`）。
  - 結果の 1 行ごとに、`<button type="button">閉じる</button>` を置く。成功（`role="status"`）にも失敗（`role="alert"`）にも付ける。押すと、その行だけを一覧から外す。ほかの行の順と中身は変えない。
  - ボタンの読み上げ名は `閉じる` だけにし、どの結果を閉じるかは、同じ行の結果のラベルを `aria-describedby` で指して補う（issue #324 の決まり：同じ名前の操作が並ぶときは、名前に対象を埋め込まず説明で補う）。
  - 閉じるのは画面の中だけの操作で、書き込み（fetch）は出さない。切断中も押せる（`disabled` にしない。確認ダイアログの「やめる」と同じく、送信につながらない操作は止めない）。
  - 自動では消さない。時間がたっても、一覧が SSE で更新されても、結果は「閉じる」を押すまで残る。
  - 閉じた後のフォーカス：閉じた行の位置に残った行（無ければ 1 つ前の行）の「閉じる」へ移す。結果が 1 件も残らないときは、ページの h1（`判断待ち`、`tabIndex={-1}`）へ移す。押したボタンが消えてフォーカスが body に落ち、キーボードの利用者が位置を見失うのを防ぐ。
  - `aria-describedby` の先の id は、行ごとに `useId` で作る。`result.key`（サーバー ID・プロジェクト名・空白を含みうる）から作らない。
  - 見た目：結果の行（`.decision-results .result`、いまは `display: flex` で折り返さない）に `flex-wrap: wrap` を足す。「閉じる」は行の右端に置き（`margin-left: auto`）、押す場所を 44px 以上（`min-height: 44px`、`min-width: 44px`）にする。「閉じる」は `.actions` の外にあるので、`.actions button` の 44px は当たらない。`.decision-results .result button` に書く。375px の幅でも、行が画面からはみ出さない。
- 理由：結果が 2 件以上あるとき、どれが最新かを時刻で読めるようにする。自動で消える表示は、読み上げや、画面を離れていた人が見落とすので、消す時を利用者が決める。
- 状態遷移：結果の一覧は「足す（置き換え）」と「閉じる」の 2 つの操作だけを受ける、画面の中の 1 つの配列で、並行も再試行も無い。下の性質のテストで、操作の列に対するモデルとの一致を確かめるので、Quint は書かない。
- PBT の性質（除外なし）：判断待ちの項目を 4 件並べたページで、種を決めた疑似乱数で「項目 i に回答して成功・失敗の結果を出す」「表示中の j 行目を閉じる」を 1 列 12 回まで並べ、各回の後に、画面の結果の行の並び（ラベル、成功か失敗か、文）が、次のモデルと一致する：
  - 結果を出す：同じ項目の行を外し、新しい行を先頭に足す。
  - 閉じる：j 行目だけを外す。フォーカスは、モデルで j 行目に来た行の「閉じる」、無ければ j-1 行目の「閉じる」、0 件なら h1。
  - 書き込みは「結果を出す」の回数と同じだけ出て、「閉じる」では増えない。
  - 「閉じる」の直後の `document.activeElement` が、上のモデルのフォーカス先と同じ。
- テストで固定すること：
  - `toDecisionResult(decision, outcome)` の結果が `at` に Date を持つ。
  - `DecisionResults` に `at` 付きの結果を渡すと、その行に `<time>` があり、文が `formatClock(at)`、`dateTime` が `at.toISOString()`。
  - 判断待ちのページ（`DecisionsContent` を jsdom にマウント）で、成功の結果と失敗の結果のどちらの行にも `閉じる` のボタンがあり、`aria-describedby` の先の文に、その行の結果のラベルが入る。
  - 成功の結果は、30 分たっても（`mock.timers` で進める）残る。
  - `閉じる` を押すと、その行だけが消え、ほかの行は残り、書き込みは増えない。切断中も押せて、同じく消える。
  - 閉じた後のフォーカスが、上の決まりのとおり（残った同じ位置の行の `閉じる`、無ければ 1 つ前、0 件なら h1）。
  - 上の PBT の性質（種 40 個）。
  - `globals.css` の `.decision-results .result` に `flex-wrap: wrap`、`.decision-results .result button` に `min-height: 44px` と `min-width: 44px`。
  - e2e（375px の幅）：判断待ちのページで回答して結果を出すと、結果の行の右端が画面の幅に収まり、「閉じる」の箱が縦横 44px 以上で、行の中にある。押すと行が消える。

### D20：アクティビティの出来事に、日ごとの見出しを入れる

元帥の決定（案 A）：日ごとに見出しを入れ、行は `HH:MM` のまま。

- いま：出来事の時刻は `HH:MM` だけ（`formatClock`）。出来事の一覧は、期間で絞らない「最新の 100 件」（`backend/src/grpc/mod.rs:74` の `ACTIVITY_EVENTS_LIMIT`、`backend/src/activity.rs:222-227` の `recent_events`。古い出来事を消す処理も無い）なので、出来事の少ない環境では 1 年以上前の出来事も混ざる。端末やサーバーの時計のずれで、`now` より先の時刻の出来事も届きうる。
- 直した後：
  - 「出来事の一覧」の節（`section[aria-label="出来事の一覧"]`）の中を、日ごとのまとまりに分ける。日ごとのまとまりは、ランドマークにしない `<div class="events-day">` で、中に `<h2 class="day-head">` と、いまと同じ `<ul class="events">`（`li.ev` の行）を持つ。`section` や `aria-labelledby` は付けない（日の数だけ region のランドマークが並ばないようにする）。見出しは h2 にし、h1 の下で段を飛ばさない（ほかの節の「日ごとの出来事」と同じ段）。行の作りと class（`ev`、`warn`、`kl`、`msg`、`sv`）は変えない。
  - 日は、まとまり（`groupActivityEvents` の 1 行）の新しい方の出来事（`newest.occurredAt`）の JST の日付で決める。日の並びは、いまの行の並び（新しい順）のまま、日が変わるところで区切る。日の中の行の並びも、いまと同じ新しい順。
  - 見出しの文は `<月>月<日>日`（0 で埋めない。例：`11月7日`）。JST の年が `now` の JST の年と違う日だけ、頭に `<年>年` を付ける（例：`2025年11月13日`、時計のずれで来年の日付なら `2027年1月2日`）。JST で `now` と同じ日だけ、後ろに `（今日）` を付ける（例：`11月13日（今日）`）。ほかの日は付けない（`昨日` も付けない）。
  - 時刻の無い出来事（`occurredAt` が無い）は、いまの並びで最後に来る（`eventTime` が 0 になる）。その行は最後の `日付不明` の見出しの下にまとめる。行の時刻は、いまと同じ `—`。
  - 行の `<time>` に、新しい方の出来事の時刻を `dateTime`（ISO 8601）で持たせる。時刻の無い行には付けない。
  - 接続の出来事をまとめた行の時刻の文：
    - 新しい方・古い方ともに時刻があり、JST の日が同じ：いまのとおり `HH:MM 〜 HH:MM`。
    - 両方に時刻があり、JST の日が違う：古い方を `MM-DD HH:MM` で書く（例：`11-12 23:50 〜 00:10`）。JST の年も違うなら `YYYY-MM-DD HH:MM`（例：`2025-12-31 23:50 〜 00:10`）。行は新しい方の日の見出しの下に置く。
    - 新しい方に時刻があり、古い方に無い（`groupActivityEvents` は時刻を見ずにまとめるため起きる）：`— 〜 HH:MM`。行は新しい方の日の見出しの下に置く。
    - 新しい方に時刻が無い（並びの上、古い方にも無い）：いまのとおり `— 〜 —`。`日付不明` の下に置く。
  - 出来事が 0 件のときは、いまのとおり `出来事はありません。` だけを出し、見出しは出さない。
  - 「日ごとの出来事」「今日の出来事（サーバー別）」の節は、この指摘では変えない（D15・D18 で変える分だけ）。
- 理由：行の幅（モバイルの幅で時刻の列が広がらない）を変えずに、どの日の出来事かを読める。年の違う日だけ年を書くので、ふだんの見出しは短いまま、1 年以上前の出来事が混ざっても見出しが重ならない。
- JST の日の境：JST の 0:00（UTC の 15:00）で日が変わる。`formatClock` と同じく +9 時間で数え、端末のタイムゾーンに頼らない。
- 状態遷移は無い（描画だけ）。Quint は書かない。
- PBT の性質（除外なし）：出来事を 0〜30 件作り、新しい順に並べて `ActivityContent` を描画し、次がいつも成り立つ（種 80 個）。時刻は、`now` の 400 日前から 2 日後（時計のずれ）までのランダムな時刻に、JST の日の境の前後 1 分、JST の年の境（12月31日 23:59・1月1日 0:00）、`now` と同じ日を多めに混ぜ、1 割ほどは時刻を無しにする。種類は接続の切断・復帰を多めに混ぜ（まとまりを作る）、サーバーとプロジェクトは 2 つずつから選ぶ。`now` も種ごとに変え、年の境の近く（1月1日 0:30 JST など）を混ぜる。
  - 見出しは重ならない（同じ文の見出しが 2 つ無い）。
  - 見出しの並びは、日付の新しい順で、`日付不明` は最後。
  - 時刻のあるどの行も、その `time` の `dateTime` の JST の年月日が、行の入っている見出しの年月日と同じ（見出しに年が無ければ `now` の年）。時刻の無い行は `日付不明` の下にだけある。
  - 行の数の合計は `groupActivityEvents` のまとまりの数と同じで、行の並びを見出しの順につなぐと、いまの 1 本の一覧の並び（新しい順）と同じ。
  - `（今日）` が付くのは `now` の JST の日の見出しだけで、多くて 1 つ。年が付くのは、JST の年が `now` と違う日の見出しだけ。
  - 行の時刻の文は、上の 4 つの書き方のどれかで、まとまりの新しい方と古い方の時刻から決まる文と同じ。
- テストで固定すること：
  - 3 日にまたがる出来事で、見出しが `11月13日（今日）`、`11月12日`、`11月7日` の順に並び、各まとまりの行がその日の出来事だけ。行の時刻は `HH:MM` のまま。
  - 日のまとまりは `div.events-day` で、`section` でも `aria-labelledby` 付きでもない。見出しは `h2.day-head`。
  - JST の日の境：`now` が `2026-11-13T15:30:00Z`（JST 11月14日 0:30）のとき、`2026-11-13T15:00:00Z`（JST 0:00）の出来事は `11月14日（今日）`、`2026-11-13T14:59:00Z`（JST 23:59）の出来事は `11月13日` の下。
  - 前の年：`now` が JST 2026年11月13日のとき、JST 2025年11月13日の出来事は `2025年11月13日` の下で、`11月13日（今日）` と別の見出し。
  - 時計のずれ：`now` より 1 日先の出来事は、その日の見出し（`11月14日`）の下で、先頭に並ぶ。
  - 日をまたぐ接続のまとまり（JST 11月12日 23:50 と 11月13日 0:10 の切断）が、`11月13日` の下の 1 行で、時刻の文が `11-12 23:50 〜 00:10`。年をまたぐまとまり（JST 2025年12月31日 23:50 と 2026年1月1日 0:10）は `2025-12-31 23:50 〜 00:10`。
  - 古い方に時刻の無い接続のまとまりは、新しい方の日の下で `— 〜 HH:MM`。
  - 時刻の無い出来事は `日付不明` の下にあり、時刻は `—`、`dateTime` が無い。
  - 0 件のときは見出しを出さない。
  - 上の PBT の性質。
  - e2e の `ul.events > li.ev`（`e2e/tests/issue-317-layout.spec.ts`）は、日ごとに `ul.events` が分かれても同じ行を拾うので、書き換えない。

## 守る不変条件

1. 同じ操作の呼び名は、画面のどこでも同じ。マージは `マージする`（一覧のボタン、確定ボタン）と、その名詞形 `マージ`（見出し、本文、理由の文、成功の文）。ゴール登録は `ゴール登録を承認する`・`ゴール登録を却下する` と、その名詞形 `ゴール登録の承認`・`ゴール登録の却下`。作業の報告は `実施した`・`対応できない`。
2. 成功の文は、backend が実際にしたことだけを言う（マージは「依頼しました」）。
3. ダイアログの見出し（読み上げ名）と確定ボタン名は同じ文にしない（既存の契約）。
4. 書き込みの確定ボタンは、「やめる」と見た目で区別できる。
5. 英語の生の値は、知らない値のときだけ出す。
6. 操作の結果は、利用者が「閉じる」を押すまで消えない。閉じるのは押した行だけで、書き込みを出さない（D7）。
7. アクティビティの出来事の行は、その行の新しい方の出来事の JST の日の見出しの下にあり、見出しは重ならず新しい日から並ぶ。年が違えば見出しの文も違う（D20）。

## Quint は書かない

文言、ラベルの写像、表示の有無、リンクの行き先、日ごとの見出しは状態遷移を足さない。D7 の「閉じる」は結果の一覧（画面の中の 1 つの配列）に「閉じる」の操作を 1 つ足すが、ループ・再試行・並行・再開に触れず、取りうる状態は「並んだ結果の列」だけなので、Quint の仕様は書かない。代わりに、操作の列とモデルの一致を性質のテスト（D7 の PBT）で確かめる。
