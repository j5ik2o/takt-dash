## 指摘ごとの変更

### D4：マージの操作の呼び名を「マージする」の 1 つにする

backend の ApproveGoalMerge は、takt の `takt_merge_goal_pr` でマージのタスクを依頼し、タスク名を返すだけです（`backend/src/grpc/writes.rs:133-169`）。応答の時点ではプルリクエストはまだマージされていません。そのため成功の文は、issue の案の「PR #N をマージしました。」ではなく「PR #N のマージを依頼しました。」にします。

| 場所 | いまの文言 | 直した後の文言 |
| --- | --- | --- |
| 一覧のボタン（`decision-actions-view.tsx:349`） | `マージを承認` | `マージする` |
| ダイアログの見出し（`:376`） | `マージの承認` | `プルリクエストのマージ` |
| ダイアログの本文（`:381`） | `プルリクエスト #418 のマージを承認します。よろしいですか。` | `プルリクエスト #418 をマージします。よろしいですか。` |
| 確定ボタン（`:382`） | `マージする` | `マージする`（変えない） |
| 成功の文（`decision-actions.ts:185`） | `マージを承認しました。` | `PR #418 のマージを依頼しました。` |
| 操作できない理由（`decision-action-builders.ts:41, 44, 49`） | `…ため、マージを承認できません。` | `…ため、マージできません。` |

- 理由：同じ操作に「承認」と「マージする」の 2 つの呼び名がある。成功の文は、backend が実際にしたこと（マージの依頼）と合わせる。
- 見出しは確定ボタンと同じ文にしない（既存の契約。ダイアログの読み上げ名と確定ボタン名が重ならない）。
- 成功の文の PR 番号は、送った操作の `payload.prNumber` から作る。
- 一覧のボタンと確定ボタンが同じ名前になる。ダイアログは `aria-modal="true"` なので読み上げでは区別できる。e2e で項目の中から一覧のボタンを探すときは、文書の順で先にある方（`.first()`）を使う。
- テストで固定すること：
  - 判断待ち一覧のマージ待ちの項目のボタンの名前が `マージする`。`マージを承認` の文が判断待ちの画面のどこにも出ない。
  - 開いたダイアログの h2 が `プルリクエストのマージ`、本文が `プルリクエスト #418 をマージします。よろしいですか。`、確定ボタンが `マージする`。
  - `submitDecisionAction(buildMergeAction(マージ待ち))` が成功したときの文が `PR #418 のマージを依頼しました。`。
  - URL・番号・ゴール ID が欠けたマージ待ちの理由の文が `…ため、マージできません。`。

### D6：確定ボタンを「やめる」と見分けられる色にする

- いま：ダイアログの「やめる」と確定ボタンは、どちらも `.actions button`（白地に灰色の線）で、見た目が同じ。
- 直した後：ダイアログの確定ボタン（マージする・ゴール登録を承認する・ゴール登録を却下する）に `class="danger"` を付ける。`.actions button.danger` は地色を `var(--orange-d)`、文字色を白（`#fff`）、線を `var(--orange-d)` にする。無効のとき（送信中・切断中）は、いまの `.actions button:disabled` と同じく押せない見た目に戻す。
- 理由：3 つの確定はどれも画面から取り消せない書き込みです。「やめる」と同じ見た目だと、押し間違いに気づけない。赤のトークンは無いので、警告に使っている `--orange-d` を使う（白との比は 4.5:1 以上）。
- 一覧のボタン（ダイアログを開くだけ）には付けない。開くだけでは書き込まない。
- テストで固定すること：
  - 3 種のダイアログで、確定ボタンが `danger` のクラスを持ち、「やめる」は持たない。
  - `globals.css` の `.actions button.danger` の地色が `--surface` ではない `var(--…)` で、文字色との比が 4.5:1 以上。

### D7：操作の結果に時刻を付ける

- いま：結果は項目ごとに 1 件ずつ一覧の上に溜まり、時刻が無いので、どれがいつの結果か分からない。
- 直した後：`DecisionResult` に、結果が出た時刻 `at: Date` を足す。`toDecisionResult(decision, outcome, at = new Date())` の 3 つ目の引数は省略できる（いまの 2 引数の呼び方はそのまま通る）。結果の 1 行に `<time dateTime="<ISO 8601>">HH:MM</time>` を出す（`formatClock`）。並びは、いまと同じく新しい結果が先頭。
- 理由：結果が 2 件以上あるとき、どれが最新かを時刻で読めるようにする。
- テストで固定すること：
  - `toDecisionResult(decision, outcome)` の結果が `at` に Date を持つ。
  - `DecisionResults` に `at` 付きの結果を渡すと、その行に `<time>` があり、文が `formatClock(at)`、`dateTime` が `at.toISOString()`。
- **判断が要る**：成功の表示を消すか、「閉じる」を付けるか。
  - 案 A：成功の表示を数秒で自動で消す。失敗は残す。
  - 案 B：成功にも失敗にも「閉じる」ボタンを付け、利用者が消す。
  - 推し：案 B。自動で消える表示は、読み上げや、画面を離れていた人が見落とす。結果は `role="status"` で読み上げるが、消える時刻を利用者が決められない。B なら時刻と合わせて、どれを読んだかを利用者が片づけられる。

### D16：run 詳細のサーバー欄にサーバーの表示名を出す

- いま：`mini` のような ID が出る。
- 直した後：`RunDetailLoader` が、layout と同じ `loadServerState()`（要求の中で 1 回の GetOverview を共有する）から `servers` を読み、`serverId` に合うサーバーの `name` を `RunDetailContent` に渡す。`RunDetailContent` の props に、省略できる `serverName?: string` を足す（いまの呼び方はそのまま通る）。引けないとき（まだ読めていない、設定から消えた）は、いまのとおり ID を出す。アクティビティの `serverLabel` と同じ代え方。
- 概要の読み取りが失敗しても（接続できない、NOT_FOUND などの gRPC のエラー）、run 詳細は出す。名前は ID で代える。`loadServerState()` は `BackendUnavailableError` だけを受け止めるので、ほかのエラーは loader が受け止める。本番では layout が同じ要求の中で先に GetOverview を呼ぶので、RPC は増えない。
- 理由：ほかの画面（概要、アクティビティ、サイドバー）はサーバーを表示名で出す。run 詳細だけ ID だと、どのサーバーか読み替えが要る。
- proto に `server_name` を足す案もあるが、layout がすでに同じ状態を読んでいるので、新しい RPC も backend の変更も要らない形にする。
- テストで固定すること：
  - 概要に `mini` → `Mac mini` のサーバーがあるとき、run 詳細ページ（`RunDetailLoader` 経由）のサーバー欄が `Mac mini`。
  - `RunDetailContent` に `serverName` を渡さないとき、サーバー欄は `mini`（ID）。
  - 概要が NOT_FOUND を返すときも、run 詳細ページは描画でき、サーバー欄は `mini`。

### D22：タスク詳細の「目的」欄を外す。戻るリンクを持ち主へ戻す

- いま：タスク詳細の `目的` 欄は h1 と同じタスク名を出すだけ（`task-detail-content.tsx:41-44`）。戻るリンクは、タスク詳細は `/goals`（`:23-25, 116-118`）、run 詳細は `/projects`（`run-detail-content.tsx:20-22, 161-163`）に決まっている。

| 画面 | 持ち主 | リンクの文 | `href` |
| --- | --- | --- | --- |
| タスク詳細 | `goalId` がある | `ゴール詳細に戻る` | `/goals/<goalId>`（`encodeURIComponent`） |

## 守る不変条件

1. 同じ操作の呼び名は、画面のどこでも同じ。マージは `マージする`（一覧のボタン、確定ボタン）と、その名詞形 `マージ`（見出し、本文、理由の文、成功の文）。ゴール登録は `ゴール登録を承認する`・`ゴール登録を却下する` と、その名詞形 `ゴール登録の承認`・`ゴール登録の却下`。作業の報告は `実施した`・`対応できない`。

5. 英語の生の値は、知らない値のときだけ出す。
