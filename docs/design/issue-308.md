# issue #308 の設計：作業の依頼の2択に確認ダイアログを足す

対象の issue：[j5ik2o/takt-dash#308](https://github.com/j5ik2o/takt-dash/issues/308)（決定は issue のコメント、2026-11-27）
関連：[j5ik2o/takt-dash#381](https://github.com/j5ik2o/takt-dash/pull/381)（切断中の操作、`specs/quint/decision-offline-actions/`）

## 何をどう変えるか

- 作業の依頼（operation_request）の「実施した」「対応できない」は、押してもすぐには送らず、マージやゴール登録と同じ `ConfirmDialog`（`frontend/web/src/components/decision-actions-view.tsx`）を開く。確定したときだけ、押した方の report で回答を送る。
- 確認の種別を足して、`DialogActionSection` と `ConfirmDialog` を使い回す。種別の名前と数（2択で1つか2つか）は実装が決める。テストは名前を書かず、2択の意図から開いた状態をそのまま使う。
- 2択のボタンが出す意図 `{ type: "answer-report", report }` は、作業の依頼では送信（`submit`）ではなく、ダイアログを開く（`resolveDecisionIntent` は `open`、`decideDecisionTransition` は開いた状態）に解決する。ボタンが `{ type: "open", dialog }` を出す形に変えてもよいが、`answer-report` も送らずに開くこと。

## 守る不変条件

1. 確定しなければ送らない。2択を押しただけ、やめる、Escape では書き込みが出ない。
2. 1回の確定で1回だけ送る。送信中は確定を押せず、二重に押しても増えない。送る report は、ダイアログに出ていた2択と同じ。
3. 切断中は送らない。開く・確定は止め、やめるだけは押せる（#307 と同じ規則）。
4. フォーカスの戻り方は既存のダイアログと同じ。開くと見出しへ移り、閉じると押したボタンへ戻る。切断中に閉じたら、押せるようになってから戻す（`decideDialogRestore`）。
5. 開いた直後の確定は送らない。ダイアログが出てから 500ms の間に確定を押しても、書き込みは出ず、ダイアログは開いたまま残る（下の「開いた直後の確定」）。

## 開いた直後の確定（Devin Review、PR #404）

一覧の「対応できない」などを2回すばやく押すと、1回目で確認ダイアログが開く。確定のボタンが、押したボタンと同じ座標に出る配置では、2回目のクリックが確定に当たり、利用者が確認を読む前に送ってしまう。マージとゴール登録の確認も同じ `ConfirmDialog` を使うので、同じ穴がある。

直し方：

- `ConfirmDialog` で、ダイアログが出てから 500ms の間は確定を受け付けない。押しても `confirm` の意図を出さず、ダイアログも閉じない。マージ、ゴール登録の承認と却下、作業の依頼の2択の、すべての確認に効く共通の直しにする。
- 「やめる」と Escape は、その間も受け付ける。
- 確定のボタンは、その間も disabled にしない。disabled はこれまでどおり送信中か切断中だけで決める（サーバー描画の性質のテストと、#307 のフォーカスの規則がこの前提で組まれている）。見た目も変えない。
- 数え始めは、ダイアログが出たとき。やめて開き直したら、数え直す。開いたまま背後の2択を押し直したとき（利用者は背景に阻まれてふつう押せない）に数え直すかは、実装に任せる。
- 受け付けは `setTimeout` で始める（壁時計に頼らない）。開くたびに受付のフラグを初めに戻し、500ms 後に受付を始め、閉じるときにタイマーを解く。前に開いたダイアログのタイマーが、開き直したダイアログを早く受け付けにしない。`Date.now()` で開いた時刻との差を測る形は採らない。`Date.now()` は端末の時計の補正を受け、開いた直後に時計が進むと、500ms たたずに確定を受け付けてしまう（CodeRabbit、PR #404）。テストは node:test の `mock.timers`（`Date` と `setTimeout`）と Playwright の `page.clock` で時計を止めて進めるので、`performance.now()` や `event.timeStamp` には頼らない。

500ms にした理由：OS の二重クリックの間隔の既定（Windows は 500ms）に合わせ、二重クリックの2回目を取りこぼさない長さにした。確認を読んで押すまでには、ふつうこれより長くかかる。

確定のボタンの位置を、押したボタンと重ならないように保つ案は採らなかった。重なるかは画面の大きさ、スクロールの位置、一覧の並びで変わり、どの配置でも重ならないことをテストで保証できない。

## 文言の案

| 押したボタン | 見出し | 本文 | 確定のボタン |
| --- | --- | --- | --- |
| 実施した | 作業の依頼への回答（実施した） | 作業の依頼に「実施した」と回答します。よろしいですか。 | 実施した |
| 対応できない | 作業の依頼への回答（対応できない） | 作業の依頼に「対応できない」と回答します。よろしいですか。 | 対応できない |

対象の行には「プロジェクト」とプロジェクト名を出す。

理由：

- 見出しは「対象の操作」（「ゴール登録の承認」）にそろえた。2択の区別は、一覧の種別名「問い合わせ（作業の依頼）」と同じ括弧の形で添えた。見出しはダイアログの読み上げ名になるので、2択で別の名前にする。
- 本文は、ほかの確認と同じ「〜します。よろしいですか。」の形にした。
- 確定のボタンは、ゴール登録（「承認」で開き、「承認」で確定する）と同じく、押したボタンと同じ言葉にした。
- 一覧には、別のプロジェクトの作業の依頼が同じボタン名で並ぶ。取り違えを防ぐため、マージの確認（#304）と同じくプロジェクトを出す。

## 変えないこと

- 「回答する」（自由記述）と、選択肢の回答。押すとすぐに送る。
- マージとゴール登録の確認の文言と動き。
- 送信の中身（`/api/decisions/answer` へ送る report の値、冪等の鍵）、backend、proto。

## 実装への注意

- `decideDialogRestore` の `triggers` は、既存のテスト（`test/components/decision-actions.test.ts`）が3つの鍵（merge と登録の2つ）だけで組む。足した種別の鍵が無くても型が通る形（`Partial` など）にし、無い鍵は `null` と同じに扱う。テストは変えない。
- 一覧のボタン名と確定のボタン名が同じになる。テストは、一覧のボタンを `[role="dialog"]` の外で探す。

## 仕様（Quint）

`specs/quint/decision-offline-actions/` に足した。項目の種類（マージか作業の依頼か）と、確定の回数（`confirms`）を持たせ、不変条件 `sendOnlyOnConfirm`（送った数 = 確定の回数）を `safety` に入れた。いまの main に当たる `withoutReportConfirm` は「作業の依頼で始まる → 2択を押す」の2手で破り、修正後の `fixed` は破らない。くわしくは同じディレクトリの README。

ダイアログの中のリンク（プルリクエストを開く）はマージの確認にだけあり、作業の依頼の確認には無い。ダイアログの中のフォーカスの移動は、リンクへはマージのときだけ移れる形にし、`focusNotOnDisabled` に「リンクにフォーカスがあるのはマージのときだけ」を足した（Devin Review、PR #404）。開いた直後の確定（時間）は仕様に含めず、単体と e2e で確かめる。

開いた直後の確定（Devin Review、PR #404）のテスト：

- `frontend/web/test/components/issue-308-operation-confirm.test.ts`：
  - ページをマウントして、作業の依頼の2択、マージ、ゴール登録の承認と却下の5つで、開いた直後と 499ms の確定は送らず、500ms の確定は1回だけ送る。やめて開き直したら数え直す。
  - 任意の操作の列の性質に、「2択を押して、時計を進めずに確定を押す」と「時計を進める（200ms と 600ms）」を足した。ダイアログが出てから 500ms たたない確定では送らない。
  - ページのテストは時計を `mock.timers` で止める。確定を押す既存のテストは、確定の前に 500ms 進める。
- `e2e/tests/issue-308-operation-confirm.spec.ts`：1回目のクリックで開いたダイアログの確定へ、2回目のクリック（detail = 2）を間を空けずに送っても届かず、ダイアログは残る。待ってから確定すれば1回だけ届く。確定を押す既存の e2e は、確定の前に 500ms 待つ。

CodeRabbit の指摘（PR #404）を受けたテストの直し：

- `frontend/web/test/components/issue-308-operation-confirm.test.ts`：
  - ページをマウントして、5つの確認で、開いた直後に壁時計（`Date`）だけを 1000ms 進めても確定は送らず、そこから 500ms 過ぎれば1回だけ送る。`Date.now()` で測る実装では落ちる。時計が戻る場合は、`mock.timers` が `Date` と `setTimeout` を1つの時計で動かす（戻すと `setTimeout` も遅れる）ため作れず、テストにしていない。
  - 任意の操作の列の性質で、開いたまま2択を押し直した時刻は、押す前にそのボタンが押せる（送信中でも切断中でもない）ときだけ覚える。切断中に押せない2択を押しても、再接続した後の確定の期待を「どちらでもよい」に緩めない。
- `e2e/tests/issue-308-operation-confirm.spec.ts`：二重クリックのテストは、クリックから確定のボタンが出るまでの実時間に頼らない。ページの時計（`page.clock`）を止めてから、1回目のクリックを送り、ダイアログの表示を条件で待ってから、確定へ2回目のクリック（detail = 2）を送る。時計を 500ms 進めてから、ふつうに確定して1件だけ届く。止めている間は Playwright のクリックが要素の安定（`requestAnimationFrame`）を待って進まないため、2つのクリックはページの中から送る。
