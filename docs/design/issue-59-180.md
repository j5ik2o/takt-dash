# issue #59 と #180 の設計：run 詳細の取得の期限を、backend の総上限と Web の deadline でそろえ、stdio の画面読み取りを要求の打ち切りから切り離す

対象の issue：[j5ik2o/takt-dash#59](https://github.com/j5ik2o/takt-dash/issues/59)、[j5ik2o/takt-dash#180](https://github.com/j5ik2o/takt-dash/issues/180)
関連：[j5ik2o/takt-dash#179](https://github.com/j5ik2o/takt-dash/pull/179)（初期化の期限を60秒に分けた）、[j5ik2o/takt-dash#390](https://github.com/j5ik2o/takt-dash/pull/390)（停止の上限18秒）、[j5ik2o/takt-dash#152](https://github.com/j5ik2o/takt-dash/issues/152)（応答なしの表示）

## 現在の main での確認（`d08c5f4`、[j5ik2o/takt-dash#390](https://github.com/j5ik2o/takt-dash/pull/390) が入った後）

コードを読んで確かめました（実機の高負荷での再現はしていません。下のテストで再現します）。

1. **Web の期限は、すべての unary で30秒。** `frontend/web/src/grpc/client.ts:146` の `DEFAULT_UNARY_DEADLINE_MS = 30_000` が `readOptions`（331-332行）を通じてすべての読み取りに効く。`getRunDetail`（216-224行）にも上書きは無い。
2. **GetRunDetail の主な経路は、takt-mcp を使わない。** `backend/src/grpc/mod.rs:417-` は保存場所を直接読む。issue の「レポート6件を順に読む」は、もう起きない（本文は GetRunContent が別に読む）。
3. **回り道は、いまも takt-mcp を何回も呼ぶ。** 保存場所の対応表に無い run（`NotListed`）と、対応表を読めない run（`Unreadable`。SSH 越しのリモートのプロジェクトなど）は、`run_detail::fill_from_takt_get_run` → `ReadSource::read_remote_run_detail`（`backend/src/grpc/resolve.rs:157-`）で、`takt_get_run` を少なくとも2回（run 本体と view instructions）、task の本文が空ならもう1回呼ぶ。stepLogs のページがあれば、その分だけ増える。1回ごとの上限は15秒（`READ_TIMEOUT`、stdio は `client_config` の `request_timeout`）。総上限は無い。呼び出しがすべて期限内でも、合計が30秒を超えれば Web が先に打ち切る（issue #59 の現象。例：3回 × 11秒 = 33秒）。
4. **stdio の画面読み取りレーンの起動と初期化は、要求の future の中にある。** 画面読み取りレーン（`registry.screen_client`）は起動時に温めない。最初の回り道の要求が、`call_tool` → `ensure_started` → `spawn` で、子プロセスを起動して initialize を待つ（上限は60秒の `INITIALIZE_TIMEOUT`、`backend/src/mcp/client.rs:138,329`）。issue #180 の前提にある「要求ごとに McpClient を作り直す」は、もう当たらない（レーンのクライアントは使い回す）。ただし、初期化が終わる前に要求が打ち切られる問題は残っている。
5. **Web の deadline は、backend の要求の future を捨てる。** tonic のサーバーは `grpc-timeout` のヘッダーで要求の future を捨てる（Web が切断しても同じ）。捨てると、次のことが起きる。
   - 初期化中なら、`spawn` の中の子プロセスは `kill_on_drop` で止まる。起動の失敗としても数えないので、次の要求がまた起動からやり直す。初期化が30秒を超える負荷が続くと、どの要求も成功しない（issue #180 の現象）。
   - 道具の呼び出し中なら、`McpClient::request` は、読みかけの子プロセスを捨てる（次の要求へ使い回さないため。`client.rs:340-` の説明）。次の要求は、また起動と初期化から始める。
6. **期限切れの表示は、経路で違う。** Web の deadline の超過は `DEADLINE_EXCEEDED` → `BackendUnavailableError("no-response")` →「backend が応答しません。読み取りが遅れている可能性があります。」と、前に読めた内容（[j5ik2o/takt-dash#309](https://github.com/j5ik2o/takt-dash/issues/309)）。一方、回り道の道具の呼び出しが15秒で時間切れになると、`fill_from_takt_get_run` は保存場所の失敗の状態を返す。`NotListed` なら `NOT_FOUND` で、画面は 404（run が無い）になる。`Unreadable` なら `UNAVAILABLE` で、「backend に接続できません」になる。

HTTP の接続先は、セッションの確立がもう別のタスクで走る（`backend/src/mcp/http.rs:436-442` の `tokio::spawn`）。要求を打ち切っても、セッションも捨てない。5 の問題は stdio だけにある。

## 何をどう変えるか

### 案の比較と決定

| 案 | #59（遅いが成功する取得） | #180（初期化が長い） | 決定 |
| --- | --- | --- | --- |
| A. Web の deadline だけを延ばす | 延ばした分だけ直る | 初期化が延ばした値を超えれば、同じく起動を繰り返す。backend には上限が無いまま | 単独では採らない |
| B. backend に総上限を設け、Web の deadline をそれより長くする | 直る（総上限の中なら成功） | 総上限で打ち切ると、初期化中・呼び出し中の子プロセスを捨てる。初期化＋呼び出しが総上限を超える負荷が続くと、起動を繰り返す（Quint の `budgetOnly`） | **採る（C と組み合わせる）** |
| C1. 初期化だけを要求から切り離す | － | 初期化は最後まで進むが、呼び出し中の打ち切りで子プロセスを捨てるので、同じく起動を繰り返しうる（Quint の `detachInitOnly`） | 採らない |
| C2. stdio の画面読み取りの「鍵の取得・起動と初期化・道具の呼び出し」をまとめて要求から切り離す | － | 要求が打ち切られても、読み取りは最後まで走り、子プロセスは使える状態で残る。次の要求は起動し直さない | **採る** |
| D. 回り道の経路だけ、初期化の上限を短くする | － | 高負荷では初期化が終わらないまま、起動を繰り返す（#179 が直した問題に戻る） | 採らない |

B と C2 を組み合わせます。Quint の仕様で、どちらか一方だけでは不変条件が破れることを確かめました（下の「状態遷移と Quint」）。

### 1. backend：GetRunDetail に総上限を設ける（`backend/src/grpc/mod.rs`）

- `pub const RUN_DETAIL_BUDGET: Duration = Duration::from_secs(45)` を置く。値は「回り道の呼び出し3回 × 1回の上限15秒」。`const _: () = assert!(...)` で `3 * READ_TIMEOUT <= RUN_DETAIL_BUDGET` を固定する。
- `get_run_detail` の本体（`resolve_run_target` から応答を組み立てるまで）を `tokio::time::timeout(self.run_detail_budget, ...)` で包む。上限に達したら、`Status::deadline_exceeded("run <slug> の詳細を <n> 秒以内に読めませんでした。takt-mcp の読み取りが遅れています。")` を返す。
- 上限はサービスの値（`run_detail_budget`、既定は `RUN_DETAIL_BUDGET`）にして、テストから短い値を入れられるようにする（`TaktDashServiceImpl::with_run_detail_budget`）。
- 打ち切ったときは、`warn` のログに run と上限を残す。
- 総上限は、ほかの RPC には付けない（範囲の外。下の「変えないこと」）。

### 2. backend：stdio の画面読み取りを、要求の打ち切りから切り離す（`backend/src/grpc/resolve.rs`）

- `ReadSource::Stdio` の各読み取り（`read_remote_run`、`read_remote_run_detail`、`read_remote_report`、`read_remote_instruction`、`read_goal_detail`、`read_task_detail`）を、`tokio::spawn` したタスクの中で行う。タスクは `handle.clone().lock_owned()` で鍵を取り、起動と初期化（`call_tool` の中の `ensure_started`）と道具の呼び出しを最後まで進める。要求は `JoinHandle` を待つだけにする。
  - **鍵を待つ間は、要求がまだ待っているかを見る**（設計レビューの指摘 1）。要求とタスクは `oneshot` でつなぐ。タスクは `tokio::select!` で「鍵の取得」と「`oneshot` の送り手の `closed()`（受け手の要求が諦めた）」を待ち、要求が先に諦めたら、鍵を取らずに道具も呼ばずに終える。こうしないと、初期化が遅い間に画面が何度も読み直したとき、諦められたタスクが鍵の待ちに溜まり、鍵が空いてから、誰も待っていない読み取りを順に流す。
  - 鍵を取った後は、要求が諦めても止めない。要求が打ち切られて受け手を捨てても、タスクは止まらない。読み取りの結果は捨てるが、子プロセスは使える状態でクライアントに戻る。次の要求は起動し直さない。
  - 引数（cwd、runSlug、ファイル名など）は所有した値にしてタスクへ渡す。
  - タスクの join の失敗（panic）は `ToolError::Transport(TransportError::Io(..))` にする。
- GetRunDetail だけでなく、同じ `ReadSource::Stdio` を通るほかの画面の読み取り（GetRunUpdates・GetRunContent の回り道、ゴールとタスクの詳細）も、同じ作りになる。どれも、Web の30秒で打ち切られると同じく子プロセスを捨てていた。
- 書き込み（`WriteSource`）は変えない（すでに `write_ledger.rs` で切り離している）。HTTP の読み取り（`ReadSource::Http`）も変えない（確立は切り離し済みで、打ち切ってもセッションを捨てない）。

### 3. backend：回り道の道具の時間切れを「応答なし」で返す（`backend/src/grpc/run_detail.rs`）

- `fill_from_takt_get_run` で `read_remote_run_detail` が `ToolError::Transport(TransportError::Timeout(_))` を返したら、保存場所の失敗の状態（`NOT_FOUND`・`UNAVAILABLE`）ではなく `Status::deadline_exceeded(..)` を返す。理由：時間切れは「run が無い」ことを意味しない。`NotListed` の run が 404 になるのは誤り。
- 画面の表示は、Web の deadline の超過と同じになる：「backend が応答しません。読み取りが遅れている可能性があります。」と、前に読めた内容（#152、#309 の表示。新しい文言は足さない）。
- 道具のエラー（`isError`）と解析の失敗、時間切れ以外の輸送エラーは、いまの扱い（保存場所の失敗の状態）のまま。
- 判定は小さな純粋関数 `remote_failure_status(local: RunReadFailure, remote: &ToolError) -> Status` にする。

### 4. Web：GetRunDetail だけ deadline を分ける（`frontend/web/src/grpc/client.ts`）

- `export const RUN_DETAIL_DEADLINE_MS = 50_000` を置く。値は backend の総上限45秒＋5秒。backend の `DEADLINE_EXCEEDED`（説明つき）が、Web の deadline より先に届く。
- `CreateBackendClientOptions` に `runDetailDeadlineMs?: number` を足す（テストから短い値を入れる）。`getRunDetail` だけがこれを使う。ほかの unary は `DEFAULT_UNARY_DEADLINE_MS`（30秒）のまま。
- backend の値と Web の値は、言語が違うので機械的にはつながらない。両方の定数の説明に、相手の定数の場所と「総上限 < Web の deadline」を書き、テストで Web 側の値が 45秒＋余裕であることを固定する。

### 変えないこと・範囲の外

- `INITIALIZE_TIMEOUT`（60秒）、`READ_TIMEOUT`（15秒）、道具ごとの期限、起動の同時数とバックオフは変えない。
- 保存場所から読める run（ふだんの経路）の挙動は変えない。takt-mcp を起動も呼び出しもしない（既存のテスト `get_run_detail_neither_starts_nor_calls_takt_mcp`）。
- ほかの RPC（GetRunUpdates、GetRunContent、ゴール・タスクの詳細）の deadline と総上限は変えない。2 の切り離しで、打ち切られても子プロセスを捨てなくなるだけ。
- 画面読み取りレーンを起動時に温めることはしない（読み取りが HTTP のプロジェクトでも子プロセスが増える。2 で、最初の要求の打ち切りが初期化を止めなくなるので、温めなくても次の要求で使える）。
- 画面の文言・表示の型は変えない（#152 の「応答なし」の表示を使う）。
- proto は変えない（`DEADLINE_EXCEEDED` は gRPC の標準の状態）。
- 待ち受けアドレス（`0.0.0.0:3000`）と接続元の制限には触らない。

## 守る不変条件

Quint の不変条件（`specs/quint/run-detail-deadline/runDetailDeadline.qnt`）と同じです。

1. **backend が Web の deadline より先に答える**（`backendAnswersFirst`）。成功か、総上限の `DEADLINE_EXCEEDED`。`RUN_DETAIL_BUDGET < RUN_DETAIL_DEADLINE_MS` が前提。
2. **子プロセスが使え、レーンも空いていた要求は、どの呼び出しも1回の期限内に終わる限り成功する**（`readyReadsWithinCallTimeoutsSucceed`。issue #59）。`3 × READ_TIMEOUT <= RUN_DETAIL_BUDGET` が前提。
3. **要求の打ち切りで子プロセスを捨てない**（`noKillByCancel`。issue #180）。初期化中でも呼び出し中でも、切り離した読み取りが最後まで進める。
4. **初期化が成功する限り、子プロセスの起動は1回**（`spawnsOnce`）。
5. **要求は総上限を超えて待たない**（`requestsAreBounded`）。切り離した読み取りの終わりを待つ（鍵を待つ）間も、総上限で返る。
7. **鍵を待つタスクの数は、待っている要求の数を超えない**（`waitingTasksBoundedByWaiters`。設計レビューの指摘 1）。
8. **要求に諦められた後で、鍵の待ちから読み取りを始めるタスクは無い**（`noReadsForAbandonedWaits`）。
6. **停止の上限（#390）を破らない。** 切り離した読み取りは鍵を持ったまま走りうる。停止の閉じる段（`shutdown_within`、15秒）は、鍵が空かないクライアントを上限で見捨てる（#390 の Quint の `busy` と同じ）。そのあとランタイムを捨てると、タスクの中の子プロセスは `kill_on_drop` で止まる。停止の全体は `STOP_DEADLINE`（18秒）のまま。Quint の仕様には停止を入れず、#390 の仕様（`specs/quint/backend-shutdown-deadline/`）の `busy` の場合に当たることを README に書く。

## PBT の性質

backend の `proptest` で、tokio の時間を止めて（`start_paused`）確かめます。除外は付けません。

1. **総上限**（`backend/src/grpc/mod.rs` のテスト。`within_budget(budget, work)` を小さな関数に切り出す）：`budget`（1〜120秒）と、仕事の長さ `work`（0〜180秒、または終わらない）を選ぶ。返る時刻は `min(work, budget)`。`work < budget` なら仕事の結果、そうでなければ `DEADLINE_EXCEEDED`。境界の `work == budget` も生成の範囲に入れる。tokio の `timeout` は内側の future を先に poll するので、同じ時刻に終わる仕事は結果を返す。境界ではこの側に倒れることを確かめる。
2. **切り離し**（`backend/src/grpc/resolve.rs` のテスト。`detached(handle, op)` を小さな関数に切り出す。鍵は本物の `tokio::sync::Mutex`）：鍵を先に持つ相手が鍵を放す時刻 `held`（0〜120秒）、仕事の長さ `work`（0〜120秒）、要求を打ち切る時刻 `cancel`（0〜120秒、または打ち切らない）を選び、要求を 1〜4 件、同じ鍵に並べる。仕事は始まると「始めた」を、終わると「終えた」を数える。
   - 鍵を取る前（`cancel < held`）に打ち切った要求の仕事は始まらない（不変条件 7・8）。
   - 始まった仕事は、打ち切られても必ず終える（`work` 秒後。不変条件 3）。
   - 打ち切らない要求は、仕事の結果を受け取る。
   - どの時点でも、鍵を待つタスクの数は、打ち切られていない待っている要求の数以下（不変条件 7。タスクの数は、`Arc` の数で数える）。
3. **回り道の失敗の状態**（`remote_failure_status`）：保存場所の失敗（`NotListed`・`Unreadable`）と、道具の失敗（時間切れの秒数 0〜u64、ほかの輸送エラー、`isError`、解析の失敗）を選ぶ。時間切れなら必ず `DEADLINE_EXCEEDED`、それ以外は `run_read_failure_status(local)` と同じ状態。

## 統合のテスト（実の mock の takt-mcp と gRPC。先に書いて、いまの main で失敗することを確かめる）

`backend/tests/run_detail_test.rs` に足します。どれも、保存場所の対応表が無い run（回り道）を使います。

4. `get_run_detail_within_the_budget_succeeds_even_when_slow`：総上限を 3秒にしたサービスで、`takt_get_run` を 0.4秒ずつ遅らせる（3回で 1.2秒）。成功する。

Web は `frontend/web/test/grpc/client.test.ts` に足します。

5. 既定の `getRunDetail` がサーバーへ送る deadline は、送った時刻から 45秒より後、50秒以内。ほかの unary（`getOverview`）は 30秒以内のまま（既存のテストの意図）。
6. `runDetailDeadlineMs` を短くすると、応答しない backend で `getRunDetail` が有限の時間で `BackendUnavailableError("no-response")` になる（既存の「応答を返さない5つの unary」のテストを、この値で動かす）。
7. backend が `DEADLINE_EXCEEDED` を返したとき、run 詳細の画面は「backend が応答しません。…」と前に読めた内容を出す（`frontend/web/test/pages/unavailable.test.ts` の既存のテストが runDetail の `DEADLINE_EXCEEDED` を扱っている。そこで足りることを確かめ、足りなければ足す）。

## 状態遷移と Quint

`specs/quint/run-detail-deadline/` に仕様とテストを置きました（`README.md` に範囲・前提・結果）。

- `runDetailDeadline.qnt`：画面1つが run 詳細の要求を順に出し、読み取りレーン1本・子プロセス1つが、起動と初期化（60秒未満）と道具の呼び出し3回（各15秒未満）を進める。要求は backend の総上限か Web の deadline で終わる。`DETACH`（`none`・`init`・`op`）で、打ち切りが読み取りをどうするかを切り替える。不変条件5つ（`safety`）と、到達の確認2つ。
- `runDetailDeadline.qnt` の `CHECK_WAITER`：切り離したタスクが、鍵を待つ間に要求を確かめるか。確かめない版（`withoutWaiterCheck`）は、設計レビューの指摘 1 の反例を出す。
- `runDetailDeadline_test.qnt`：筋書き10件。修正前の2つの現象（33秒の取得が30秒で打ち切られる、40秒の初期化が終わらず起動を繰り返す）、期限だけ・初期化の切り離しだけの版の反例、修正案での回復と、鍵を待つ要求も総上限で返ること。

## 壊しうる入力の一覧

- **期限の境界**：仕事がちょうど総上限で終わる（結果を返す側に倒れる。PBT 1）。呼び出し3回がそれぞれ15秒の直前で終わる（合計 45秒未満で成功。Quint）。
- **初期化の長さ**：0秒、総上限より長く 60秒未満（要求は総上限で返り、次の要求が使う）、60秒ちょうど（初期化の期限切れ。いまの扱いのまま、起動の失敗としてバックオフ）。
- **並行**：切り離した読み取りが鍵を持っている間に、同じレーンへ次の要求が来る（鍵を待ち、総上限で返る。Quint の `requestQueuedBehindADetachedOpIsBoundedTest`）。その間に画面が何度も読み直す（諦められたタスクは鍵の待ちをやめる。Quint の `abandonedWaitsLeaveWithWaiterCheckTest`、PBT 2）。レーンが複数（`screen_read_lanes`）なら、別のレーンの要求は待たない。
- **再開・再試行**：打ち切りの直後の画面の自動更新（状態の配信で `router.refresh`）。切り離した読み取りが終わる前なら鍵を待ち、終わった後なら使える子プロセスで読む。
- **停止**：切り離した読み取りの途中で停止の合図（#390 の `busy` の場合。上の不変条件 6）。
- **ページの多い run**：stepLogs のページが多い run は、総上限を超えて `DEADLINE_EXCEEDED` になる。切り離した読み取りは、上限 `MAX_PAGES`（100）と1回 15秒の範囲で最後まで走り、その間レーンの鍵を持つ（同じレーンのほかの読み取りは待つが、総上限・Web の deadline で返る）。
- **打ち切った要求の結果**：切り離した読み取りの結果（成功も失敗も）は捨てる。状態ストアやキャッシュには書かない（いまも書かない）。
- runSlug・ファイル名などの文字列の形は変えない（入力の検証はいまのまま）。

## 上流・保存済みデータ・公開 API・守りの仕組みへの影響

- 上流（takt、takt-mcp）：変更なし。takt-mcp への呼び出しの回数と順は変えない。打ち切った要求の分の呼び出しは最後まで送る（いまは途中で子プロセスごと捨てていた）。
- 保存済みのデータ：変更なし（SQLite、状態ストア、run の保存場所に書かない）。
- 公開 API：proto は変えない。GetRunDetail が `DEADLINE_EXCEEDED` を返す場合が増える（総上限、回り道の時間切れ）。いままで `NOT_FOUND`（404）や `UNAVAILABLE` だった回り道の時間切れが `DEADLINE_EXCEEDED` に変わる。Web はどちらも扱える。crate の中で `RUN_DETAIL_BUDGET`、`TaktDashServiceImpl::with_run_detail_budget` を足す。Web の `CreateBackendClientOptions` に `runDetailDeadlineMs` を足す。
- 守りの仕組み（CI・関門・ルールセット）：変更なし。テストの土台（`backend/tests/grpc_harness`）に、総上限を入れてサーバーを起動する関数を足す。
