# taktDash 要件定義（確定版）

- 状態は要件確認済みであり、この文書は2026-11-14時点の確定内容である。
- 2026-11-24に、オーナー裁定（[#313](https://github.com/j5ik2o/takt-dash/issues/313)）に基づき、対象サーバーを Mac mini 単体へ改めた。Mac Studio は現行要件の対象外である。1〜4章と6章はこの裁定に合わせてあり、5章の質疑は当時の記録として残す。
- この文書は、加藤潤一と窓口の質問と回答で確定した事項と、カスタム版 takt のソースコードで確認した事実を記録する。

## 1. 目的

taktDash は、Mac mini で動く複数プロジェクトの takt manager の状態を1つの画面へ集約するダッシュボードである。taktDash は判断待ちの問い合わせへの回答と、プルリクエストのマージ承認と、ゴール登録の承認・却下を画面から行えるようにする。手本は sparkDash であり、sparkDash の使いやすさの本質は、開いた瞬間に全体の状態が見えることと、正常なものは静かで異常なものだけが目立つことである。

## 2. 確定した要件

### 2.1 集約対象のサーバーとプロジェクト

- 集約対象は Mac mini 1台である。Mac Studio は現行要件の対象外であり、Mac Studio の集約・SSH 接続・配置を必須条件にしない。
- 設定は複数のサーバーを表せる形のまま保つ。ただし、現行要件で集約するサーバーは Mac mini だけである。
- DGX Spark と Ubuntu 機（RTX4090）は最初の版の対象にしない。画面モックに描かれた4台の数字はダミーデータである。
- すべてのプロジェクトを Mac mini が担当する。サーバーとプロジェクトの対応と対象プロジェクトの一覧は taktDash が設定として持ち、画面ではこの対応に沿って集約する。
- 2026-11-24に確認した運用中の設定では、Mac mini が takt・takt-dash・modern-ddd-book・fraktor-ng-rs・ddd-principles を担当する。リポジトリの taktdash.config.example.json のプロジェクトは書き方の例であり、運用中の一覧ではない。

### 2.2 操作

- taktDash は最初の版を読み取り専用にしない。
- ユーザーは判断待ちの問い合わせへ taktDash の画面から回答できる。
- ユーザーはプルリクエストのマージ承認を taktDash の画面から行える。マージには takt-mcp の takt_merge_goal_pr を使う。
- ユーザーはゴール登録の承認と却下を taktDash の画面から行える。ゴール登録の承認待ちも判断待ちの一覧に表示する。
- 操作 UI は判断待ちページの一覧から直接操作する形とする。選択肢のある質問は選択肢ボタン、自由記述の質問はテキスト入力、作業の依頼（operation_request）は「実施した」「対応できない」のボタンとする。マージ承認とゴール登録の承認・却下には確認ダイアログを挟み、実行結果の成功・失敗は画面上に表示する。
- CLI も最初の版から全機能を持ち、Next.js と同じ操作（状態の閲覧・問い合わせ回答・マージ承認・ゴール登録の承認と却下）を行える。
- takt manager と takt director の起動・停止・自動起動は最初の版の対象外とし、後の版で検討する。自動起動は taktDash の機能にせず、launchd など OS 側の設定で担保する。

### 2.3 構成

- taktDash はバックエンド部分とフロントエンド部分に分かれる。バックエンドは API サーバであり、フロントエンドは UI を提供する。
- バックエンドは1つだけ置き、サーバーとプロジェクトの集約はバックエンドが担う。フロントエンドはバックエンドの API だけを使い、フロントエンドは takt-mcp へ直接つながらない。
- バックエンドは Rust で実装し、tonic による gRPC を API とする。API 定義は .proto で一元管理する。
- フロントエンドは Next.js と CLI の2つである。
- Next.js はサーバー側（RSC・Route Handlers）が gRPC クライアントとして Rust バックエンドと通信する BFF 構成とし、ブラウザから Rust バックエンドへは直接接続しない（gRPC-Web は使わない）。画面はレスポンシブとし、モバイルからも見えるようにする。
- CLI は Rust で実装し、バックエンドと同じ .proto から生成したクライアントでネイティブ gRPC により接続する。
- 開いている画面への自動更新は、gRPC のサーバーストリーミングで状態を push し、Next.js の Route Handler がそのストリームを SSE に中継してブラウザへ届ける。初回接続時は即時に全件を返す。
- ネイティブの iOS 版と Android 版は後の版で出す。最初の版の範囲には含めないが、同じ gRPC API から使えることを念頭に API を設計する。

### 2.4 データ源

- バックエンドは takt-mcp の道具で状態を取る。バックエンドが取る状態は、ゴールとタスクと run と保留中の質問であり、run のログの末尾とレポートの本文も takt_get_run で取得できる。各道具は cwd でプロジェクトを選ぶ。
- バックエンドは同じ Mac mini の上の takt-mcp と話す。接続方法は、takt-mcp を子プロセスとして起動して標準入出力で話す stdio 接続と、Mac mini 上に常駐する takt-mcp の HTTP サーバー（127.0.0.1 で待ち受ける）へつなぐ HTTP 接続の2つであり、設定で選ぶ。
- 2026-11-24に確認した運用では、読み取りと書き込みの両方を Mac mini 上の常駐 HTTP サーバーへ向けている。HTTP サーバーの認証情報は設定ファイルにだけ持ち、文書とリポジトリには書かない。
- 読み取りと操作を同じ接続で行うため、takt-mcp の道具の範囲は read-only ではなく操作を含む tool-set（manager または all）と、4章の追加道具を使う。
- run 詳細ページのログ（本体・provider-events・usage-events の JSONL）と、24時間トークン集計に使う usage-events の JSONL は、バックエンドが Mac mini 上のファイルをローカルで直接読む。対象の run が worktree で動く場合は worktree 側の .takt/runs を読む。
- アクティビティの履歴は taktDash が Mac mini 上の SQLite に永続化する。バックエンドは読み取りのたびに検出した出来事（ゴール登録・run 開始・タスク完了・問い合わせ・マージ待ち・一時停止・blocked・接続断）を記録し、7日分の日次集計と出来事の一覧を SQLite から出す。接続の出来事も同じ仕組みで taktDash が記録する。
- サーバーから応答がない間は、最後に読めた時点の状態をキャッシュとして保持し、読めた時点の時刻とともに画面へ表示する。
- バックエンドが takt-mcp へつなぐ設定は、.mcp.json と同じ mcpServers 形式の設定ファイルで持つ。stdio 接続は command に node を指定して takt-mcp を直接起動し、HTTP 接続は type を http として常駐サーバーの URL と Authorization ヘッダを指定する。プロジェクトとサーバーの対応・各プロジェクトの cwd・ログを読む .takt のパス・読み取り間隔・異常判定の閾値も同じ設定ファイルに持つ。

### 2.5 画面

- 画面の基準は docs/taktdash.html のモックと docs に置かれた画像3件である。ページは概要と判断待ちとプロジェクトとアクティビティと run 詳細の5つである。
- 概要ページの「24時間のトークン消費」（モデル別の内訳を含む）は最初の版から実装する。Mac mini 上の各プロジェクトの usage-events の JSONL を読み、バックエンドが集計する。

### 2.6 配置とアクセス

- taktDash（バックエンド・Next.js・SQLite）は Mac mini で動かす。takt-mcp と .takt のファイルも同じ Mac mini の上で扱い、別のサーバーへの SSH 接続を前提にしない。
- アクセス範囲は自宅 LAN と Tailscale の両方とし、外出先のモバイルからも利用できる。
- 認証は設けない。利用者は加藤1人であり、Tailscale の認証と ACL を防御とする。問い合わせ回答・マージ承認・ゴール登録の承認と却下の操作系 API も同じポリシーとする。

### 2.7 データの新しさと異常判定

- バックエンドは Mac mini の takt-mcp から30秒ごとに状態を読み取る。
- 異常判定の基準はモックの値を採用する。判断待ちの滞留は4時間（240分）以上、ログの無音は10分超とする。これらは takt の基準ではなく taktDash の基準であり、設定で変更できるようにする。

## 3. takt-mcp についてソースコードで確認した事実（2026-11-14）

この章は2026-11-14時点の確認結果である。その後、takt-mcp には常駐 HTTP サーバーとして動く形が加わり、現行の運用はこれを使う（2.4を参照）。別のサーバーの takt-mcp を呼ぶ配管の記述は当時の検討であり、現行要件ではない。

- takt-mcp の単体プログラムは stdio 接続専用であり、takt-mcp はネットワークの待ち受け口を持たない。道具の範囲は起動時の引数 --tool-set で all と read-only と manager の3種類から選べる。
- 同じサーバーの上では、バックエンドは takt-mcp を子プロセスとして起動して直接話せる。別のサーバーの takt-mcp を呼ぶには、バックエンドはそのサーバーの上で takt-mcp を起動して標準入出力を運ぶ配管を必要とし、SSH は配管の候補の1つである。
- manager と director の内部には、そのホストの中だけで使う HTTP 接続の仕組みがある。この仕組みは manager 自身の会話実行が使う内部接続であり、この仕組みは外部のダッシュボード向けの安定した接続点ではない。
- takt-mcp にはトークン使用量を集計する道具が無い。モデル別24時間トークン表示は usage-events の JSONL ファイルを読んで実現する。
- takt-mcp には判断待ちの質問へ回答する道具が無い。質問の一覧と取得の道具はある。プルリクエストのマージについては takt_merge_goal_pr の道具がある。
- ゴール登録の承認待ちは takt-mcp から見えない。

## 4. takt 側の先行作業

takt-dash の最初の版の実装に先立ち、カスタム版 takt リポジトリの側で次の道具を takt-mcp に追加する。追加した道具と、manager の会話を読む道具（バックエンドが保存場所を直接読む経路を含む）を Mac mini へ配置するところまでが、takt-dash 実装開始の前提条件である。Mac Studio への配置は前提条件に含めない。

- 判断待ちの問い合わせへ回答する道具。
- ゴール登録の承認待ちを一覧で取得する道具。
- ゴール登録を承認する道具と却下する道具。
